# ARCHITECTURE — ALSAVI

Источник архитектурной истины проекта. Терминология и принципы наследуются из
[`PROJECT_CONSTITUTION.md`](PROJECT_CONSTITUTION.md) (commit `00972bb`), раздел
CORE ARCHITECTURE. Этот документ описывает **фактическое** состояние кода, а не
планы. Разработчику, впервые открывшему проект, стоит читать вместе с
[`ENGINE.md`](ENGINE.md) и решениями в [`docs/adr/`](docs/adr/).

> Статус на момент написания: Phase 1 (Learning Engine + web MVP), после
> TASK_001 (in-session Learning Steps через StudySession). AI Layer ещё не
> реализован.

---

## 1. Общая модель

ALSAVI построен вокруг одного детерминированного ядра памяти —
`LearningEngine` — и набора **независимых потребителей** его публичного API.

**Ключевая формулировка (из конституции, обязательна во всех документах):**
AI Layer — **не последовательный слой, через который проходит память**, а
**отдельный потребитель публичного API `LearningEngine`, равноправный с UI и
StudySession**. Любой потребитель (UI, StudySession, AI Layer) обращается к
Engine **только через публичный интерфейс** — никогда напрямую к хранилищу.

Потребители **не выстроены в цепочку** `Engine → StudySession → UI → AI`. Каждый
обращается к ядру самостоятельно. StudySession и AI Layer — параллельные
потребители одного ядра, а не звенья одной цепи.

## 2. Диаграмма

```
        Потребители публичного API LearningEngine
        (независимы; ни один не проходит «сквозь» другой)

  ┌────────────┐ ┌──────────────┐ ┌──────────────┐ ┌────────────────────┐
  │  UI (web)  │ │ StudySession │ │ anki-import  │ │ AI Layer (read-only│
  │ReviewSession│ │ (поток сессии│ │ (Parser +    │ │ consumer, TASK_010)│
  │ CardManager│ │  + bury)     │ │  Mapper)     │ │ AIService.answer() │
  └─────┬──────┘ └──────┬───────┘ └──────┬───────┘ └─────────┬──────────┘
        │               │                │                   │
        │              только публичный API (addNote/review/…)│
        └───────────────┴────────┬───────┴───────────────────┘
                                 ▼
                  ╔═══════════════════════════════╗
                  ║        LearningEngine          ║
                  ║  детерминированное ядро памяти  ║
                  ║  (addCard, review, getDueCards, ║
                  ║   previewIntervals, getStats…)  ║
                  ╚═══════┬───────────────┬════════╝
                          │               │
                 Scheduler│               │EngineStore
                (алгоритм SRS,            │(порт хранилища,
                 заменяем)                │ заменяем)
                          ▼               ▼
                   FsrsScheduler   MemoryStore (тесты)
                   (ts-fsrs)       DexieStore (web/IndexedDB)
```

Примечание: UI фактически **композирует** StudySession (спрашивает у него
«какую карточку показать») и одновременно сам вызывает Engine (записать ответ,
превью интервалов, статистика). Но StudySession **никогда** не стоит между AI и
ядром — каждый потребитель говорит с ядром напрямую. Именно это и означает
«параллельные потребители».

## 3. Architecture Principles

1. **Детерминированное ядро.** `LearningEngine` и его `Scheduler` не содержат
   случайности (FSRS fuzz выключен). Одинаковая история → одинаковое расписание.
2. **Автономность ядра.** Ни одного импорта сети или AI в `packages/engine`.
   Проверяется тестом `layer boundary`.
3. **Доступ только через публичный API.** Потребители не читают и не пишут в
   хранилище напрямую.
4. **Обратимость через порты.** Алгоритм за `Scheduler`, хранилище за
   `EngineStore`. Реализацию можно заменить, не трогая контракт.
5. **Разделение осей изменения (SRP).** Расчёт памяти (Engine) и поток учебной
   сессии (StudySession) меняются по разным причинам и живут раздельно
   (см. [ADR-003](docs/adr/ADR-003-studysession-separation.md)).
6. **Локальность и скорость.** Всё, что можно, считается локально и мгновенно.
7. **Простота прежде архитектурной чистоты** (порядок приоритетов конституции),
   кроме границы «Engine ↔ потребители», закладываемой с первого дня.
8. **Минимальный публичный API ядра.** `LearningEngine` предоставляет минимальный
   публичный API, необходимый существующим потребителям; он не стремится быть
   универсальным query-слоем. Политика выбора, интерпретации и порядка обработки
   данных остаётся ответственностью потребителей, таких как `StudySession`.

## 4. Architecture Invariants

Инварианты, которые нельзя нарушать без отдельного обсуждения контракта:

- **INV-1.** `packages/engine` не импортирует сеть/AI (enforced: тест
  `layer boundary` в `engine.test.ts`).
- **INV-2.** Планирование детерминировано; изменение планирования допускается
  только с тестом на регрессию расписания.
- **INV-3.** Редактирование контента (`updateNoteContent`) **никогда** не
  изменяет scheduling-состояние (enforced тестом).
- **INV-4.** Review Log — append-only, source of truth. Scheduling-состояние
  карточки — кэш.
- **INV-5.** `CardState` фиксируется в каждом `Review` (`stateBefore`/
  `stateAfter`) и воспроизводим из лога через `rebuildCardState` (см. §10).
- **INV-6.** StudySession и AI Layer обращаются к ядру только через публичный
  API; StudySession не рассчитывает расписание и не пишет в хранилище.
- **INV-7.** Если AI Layer недоступен — Engine и StudySession работают в полном
  объёме.
- **INV-8.** Контент принадлежит `Note` (единственный источник истины); `Card`
  не хранит `front/back`, а рендерит их из заметки. Редактирование контента
  никогда не изменяет scheduling (обновлённая форма INV-3).
- **INV-9.** Восстановление из бэкапа безопасно: файл **полностью валидируется
  до** любой записи; замена — атомарная (одна Dexie `rw`-транзакция, откат при
  сбое), поэтому падение в середине оставляет прежние данные целыми. Сырой
  `indexedDB.deleteDatabase` не используется — deadlock из TASK_007 исключён по
  построению. История удалённых карточек (повторения без карты, TASK_027)
  восстанавливается целиком, но только если файл её **явно объявил**
  (`retiredReviews`, версия 2) или пользователь подтвердил её в старом файле
  версии 1 (§11b).

## 5. LearningEngine (`packages/engine/src/engine.ts`)

Детерминированное ядро памяти и единственная точка входа к картам и расписанию.
Публичный API:

| Метод | Назначение |
|---|---|
| `addNote({front, back, example?, memo?, tags?, directions?})` | создать заметку + 1..N карт (due сразу, `new`); теги нормализуются |
| `addCard({front, back, deckId?})` | сахар: одна forward-карта (Note 1:1) |
| `updateNoteContent(noteId, {front, back, example?, memo?, tags?})` | правка контента заметки (тот же id) → все сёстры; пишет только заметку — карты, scheduling и лог не трогаются |
| `archiveNote(noteId)` / `unarchiveNote(noteId)` | архив (TASK_023): карты заметки уходят из due-запросов и счётчиков карт / возвращаются; ничего не удаляется, расписание и лог целы; идемпотентно |
| `updateCardContent(id, …)` | `@deprecated` мостик: только forward без сестёр, иначе ошибка |
| `deleteCard(id)` | удалить карту (+ заметку, если последняя); лог сохраняется. **UI не использует** (TASK_023): у карты с историей оставляет в логе повторения без карты — бэкап выносит их в `retiredReviews` (TASK_027, §11b) |
| `deleteNote(id)` | удалить заметку и её карты; лог сохраняется |
| `getNote(id)` / `getCard(id)` / `listCards()` | чтение |
| `getCardView(id)` / `listCardViews()` | карта(ы) с контентом из заметки + сама заметка `view.note` (список — batch-загрузка заметок; архивные включены) |
| `getDueCards(limit?)` | карты активных заметок с `due <= now`, по возрастанию `due` |
| `getCardsDueBy(threshold)` | индексированный факт-запрос `due <= threshold` по картам активных (не архивных) заметок (для learn-ahead StudySession) |
| `review(cardId, rating)` | записать ответ: пересчёт + append в Review Log |
| `previewIntervals(cardId)` | due-даты для каждого рейтинга (для кнопок) |
| `getStats()` | totalCards, newCards, dueNow (по активным картам), reviewsToday, accuracy, streak (по всему логу); определения дня/успеха/серии — общие с `getLearningStats` (§5b) |
| `getLearningStats()` | статистика для экрана «Статистика» (TASK_026, TASK_031): сегодня, серии, активность за 7/30 дней, карты по состояниям, трудные слова, ответы за всё время, изученные слова, карты к повторению; read-only, чистая функция `computeLearningStats` (§5b) |
| `countNewCardsAnsweredSince(dayStart)` | уникальные карты с первым (`stateBefore === 'new'`) ответом `>= dayStart`; для дневного лимита `StudySession` (TASK_020), derived, не персистится |

Зависимости внедряются: `store: EngineStore`, `scheduler?` (по умолчанию
`FsrsScheduler`), `now?()`, `newId?()` — часы и генератор id инъектируются ради
детерминизма/тестируемости.

## 5a. Note → Card (модель контента)

`Note` (`packages/engine/src/types.ts`) — **единственный источник истины для
контента**. Одна заметка порождает одну или несколько карт (`forward`/`reverse`
через `addNote({directions})`). `Card` **не хранит** свой `front/back`: они
вычисляются из заметки чистой функцией `renderCard(card, note)`
(`render.ts`). Следствия:

- редактирование `updateNoteContent` мгновенно отражается на всех картах-сёстрах
  — дрейф контента структурно невозможен;
- у каждой карты заметки **своё независимое** планирование и `state` (Scheduler и
  Review Log работают пер-карта — Note им невидим);
- UI берёт готовый контент через `getCardView`/`listCardViews` (рендер — в ядре).

`Deck` (пока строка `deckId` на карте) и `CardType` (система шаблонов) как
сущности **не** реализованы: `template` — ограниченный enum `forward|reverse`.
Модель допускает их добавление позже без ре-миграции Note.

**Необязательные поля и архив (TASK_023).** `Note` получила необязательные
`example`, `memo`, `tags`, `archivedAt`. Обратная совместимость — без миграции:
схема Dexie не менялась (поля не индексируются), старые строки читаются как
есть, ядро отдаёт отсутствующие `tags` как `[]`. Теги нормализуются ядром на
каждой записи (`normalizeTags`, `packages/engine/src/tags.ts`). `renderCard`
по-прежнему отдаёт только `front/back`. Пример и личную заметку (`view.note`)
показывает UI-сессия — только после «Показать ответ», в обоих направлениях
(TASK_024, `apps/web/src/review-flow.ts`); на планирование и порядок показа
они не влияют.

Удаление из активной базы — **архив**, а не физическое удаление:
`archiveNote` ставит `archivedAt` и только; заметка, карты (со scheduling) и
Review Log остаются, поэтому INV-4/INV-5 и ссылочная целостность бэкапа
сохраняются по построению. Исключение архивных карт происходит в ядре, в
due-запросах (`getDueCards`/`getCardsDueBy`), — `StudySession`, его порядок
выборки, learn-ahead, bury и дневной лимит не менялись; без архивных заметок
результат запросов идентичен прежнему (порядок сохраняется). Поиск, фильтры и
проверка дублей — политика потребителя (`apps/web/src/card-list.ts`) поверх
`listCardViews()` (принцип №8: ядро — не query-слой).

## 5b. Статистика обучения (`packages/engine/src/stats.ts`, TASK_026)

Статистика — **read-only производная** от данных, которыми ядро уже владеет:
карт (scheduling-кэш), заметок (архив) и Review Log. Чистая функция
`computeLearningStats({cards, notes, reviews, now}, startOfDay?)` ничего не
пишет, не кэширует и не планирует; `LearningEngine.getLearningStats()` только
читает три коллекции через `EngineStore` и вызывает её. UI
(`apps/web/src/StatsScreen.tsx`) лишь раскладывает готовые числа; формулировки,
склонения и высоты столбцов — в `apps/web/src/stats-view.ts`.

Почему в ядре, а не в UI: Review Log доступен только через `EngineStore`, а
потребители к хранилищу не обращаются (INV-6, принцип №3). Открыть
`listReviews()` наружу значило бы превратить ядро в query-слой (принцип №8) и
размножить определения по потребителям. Один read-only метод с готовой
моделью — меньший контракт. Отдельный `StatsService` поверх доменных событий
(roadmap M4) не вводился: слоя M0/событий нет, ADR-005 — Proposed.

**Нормативные определения** (комментарий модуля `stats.ts` — источник):

- **успешный ответ** — `hard`, `good`, `easy`; **неуспешный** — `again`
  (`isSuccessfulRating`; на нём же `getStats().accuracy`);
- **день** — локальный календарный день устройства, от полуночи до полуночи
  (`startOfLocalDay`, та же граница, что у дневного лимита TASK_020); дни
  перехода на летнее/зимнее время (23/25 ч) — один день;
- **учебный день** — день с хотя бы одной записью в Review Log; открытие
  приложения без ответа не считается;
- **текущая серия** — учебные дни подряд, заканчивающиеся сегодня; если
  сегодня ответов ещё нет — заканчивающиеся вчера (день не закончился, серия
  не прервана); `reviewedToday` различает эти случаи. `getStats().streakDays`
  — то же значение (до TASK_026 серия обнулялась утром до первого ответа);
- **самая длинная серия** — самый длинный отрезок подряд идущих учебных дней
  в журнале;
- **активность** — ровно 7 и 30 последних дней, включая сегодняшний, от
  старого к новому; дни без повторений присутствуют с нулём;
- числа по журналу (сегодня, серии, активность) учитывают **все** записи,
  включая карточки, позже убранные в архив; **карточки** и **трудные слова** —
  только активная коллекция. Группы карт не пересекаются: `new` / `learning`
  (+`relearning`) / `review` с наступившим сроком / `review` в ожидании;
  архивные считаются отдельно;
- **трудное слово** — активная заметка, у карт которой `scheduling.lapses > 0`
  (тот же признак, что фильтр «Трудные» в «Карточках»); ранжирование по сумме
  lapses карт заметки, до 5 слов.
- **изученная карточка** (TASK_031) — состояние FSRS `review`: карта прошла
  шаги изучения и повторяется на длинных интервалах; забытая карта уходит в
  `relearning` и перестаёт быть изученной, пока снова не выпустится. Порога
  стабильности/интервала сверх состояния планировщика нет;
- **изученное слово** (TASK_031) — активная заметка, у которой **все** карты
  в `review` (с обратной карточкой — оба направления); заметка без карт не
  изучена. Счётчик `notes.learned` из `notes.active`;
- **к повторению сейчас** (TASK_031) — активная карта, на которую уже
  отвечали (`state !== 'new'`), со сроком `due <= now`: изученные с подошедшим
  сроком и изучаемые, у которых подошёл следующий шаг. Новые считаются
  отдельно (их выпускает дневной лимит), остальные — `due.later`;
  `due.now + due.later + cards.new === cards.active`. Это не очередь
  `StudySession.overview()` (там дневной лимит, learn-ahead и bury) — поэтому
  на Главной и в «Статистике» числа могут немного различаться;
- **ответы за всё время** (TASK_031) — `answers.total` / `answers.successful`
  по всему журналу (архивная история включена); точность = их отношение, то
  же значение, что `getStats().accuracy`; деление делает потребитель.

Календарь (`startOfDay`) инъектируется только ради тестов: так проверяется
фиксированный часовой пояс независимо от машины. Тесты (`stats.test.ts`)
задают время локальными компонентами даты и проходят в любых поясах
(проверено в 9, включая DST Европы/США и сдвиг +30 мин Lord Howe).

## 5c. Тренировка трудных слов (`apps/web/src/practice-flow.ts`, TASK_032)

Дополнительная практика **вне** интервального повторения. Это потребитель
публичного API только на чтение: единственный вызов ядра —
`listCardViews()` в `loadDifficultPractice` (тип `Pick<LearningEngine,
'listCardViews'>`). Выборка — карты активных заметок с `scheduling.lapses > 0`
(тот же признак «трудного», что в §5b и фильтре «Трудные»). Контроллер
`PracticeController` получает только загрузчик карточек — ни `LearningEngine`,
ни `StudySession`, — поэтому записать ответ, сдвинуть `due`, изменить
состояние FSRS, счётчик дневного лимита (`countNewCardsAnsweredSince`) или
очередь он не может по построению. Самооценки «Не помню / С трудом / Помню» —
не `Rating`, живут только в памяти контроллера и в Review Log не попадают;
статистика их не видит. Тесты (`practice-flow.test.ts`) сравнивают полный
снимок хранилища, очереди и статистики до и после тренировки и проверяют, что
обычная сессия после тренировки выдаёт те же карты с теми же интервалами.

«Повторить слова с ошибками» (TASK_033) — `PracticeController.retryStruggled()`:
новый раунд только из карточек, оценённых «Не помню» / «С трудом» в
завершённом раунде. Карточки перечитываются тем же загрузчиком (архивная за
это время выпадает) и перемешиваются; запись по-прежнему невозможна по
построению.

## 6. StudySession (`packages/engine/src/study-session.ts`)

**Детерминированный слой учебного потока.** Отвечает за то, *какую карточку
показать следующей*, — но не за то, *как считать память*.

- Публичные методы: `nextCard()`, `dueCount()`, `answer(cardId, rating)`,
  `newCardsWithheldByLimit()`, `setNewCardsPerDay(limit)`.
- Политика выборки: сначала реально due-карточки (`due <= now`, порядок по
  `due`, tie-break по `id`); иначе — learning/relearning-карточка в окне
  learn-ahead (`learnAheadMinutes`, по умолчанию 20). Не-due review/new карты
  досрочно не показываются.
- **Дневной лимит новых карт (TASK_020), owner-approved первый slice `M1: Daily
  Study Controls`** (реализован как политика `StudySession` согласно
  [ADR-003](docs/adr/ADR-003-studysession-separation.md) — Accepted — а не как
  `StudyService`/`SettingsService` из буквального task breakdown roadmap,
  который назначал их на `M0`; см.
  [docs/ROADMAP_ALSAVI_BETA.md](docs/ROADMAP_ALSAVI_BETA.md) §4 M1 и
  `tasks/TASK_020.md`):
  - `newCardsPerDay: number | null` — `null` = unlimited (default), `0` =
    ноль новых карт сегодня, положительное целое — дневной лимит. Только
    `null`/`undefined` означают unlimited; `0` — значимое значение, никогда не
    трактуется как falsy.
  - Usage **derived**, не персистится: уникальные `cardId`, чей первый
    (`stateBefore === 'new'`) ответ записан с `reviewedAt >=` границы
    локального календарного дня (`engine.countNewCardsAnsweredSince(dayStart)`
    — тот же `startOfLocalDay`, что и `getStats().reviewsToday`/streak).
    Показ новой карточки без ответа allowance не расходует — осознанное
    ограничение производной от Review Log семантики.
  - Ограничивает только `state === 'new'` карты внутри `dueNow`; due-карты
    вне `new` и learning/relearning (включая learn-ahead) не затрагиваются.
  - `newCardsWithheldByLimit()` — производный от того же селектора, что
    `nextCard()`/`dueCount()`, read-only сигнал для UI (сколько новых карт
    удержано лимитом прямо сейчас) — различает «ничего не due» от «новые
    карты есть, но лимит их удерживает» без риска рассинхрона.
  - `setNewCardsPerDay()` — узкий mutable setter; применяется к следующей
    выборке без пересоздания `StudySession` и без сброса bury-состояния.
  - Persistence: `settings`-таблица в существующей `AlsaviDB` (аддитивный
    Dexie `version(3)`), вне порта `EngineStore`; `replaceAll` (restore)
    таблицу не трогает — restore не сбрасывает setting, usage пересчитывается
    из восстановленного Review Log. Backup schema — без изменений
    (`BACKUP_VERSION = 1` на момент TASK_020); setting не входит в backup ни
    одной версии (версия 2 из TASK_027 добавила только `retiredReviews`).
- **Bury siblings:** после ответа сёстры отвеченной карты (та же `noteId`, кроме
  самой карты) не показываются до конца сессии; `dueCount()` их исключает
  (инвариант TASK_002 сохранён); единственная оставшаяся погребённая сестра не
  показывается — сессия завершается. Состояние bury — эфемерные in-memory `Set`
  на экземпляре, **не персистится**; границы сессии = время жизни экземпляра
  `StudySession`, а не календарное время.
- `answer()` — **оркестратор**: делегирует запись в `engine.review()` (единственный
  writer в Review Log/scheduling/CardState) и обновляет только своё bury-состояние;
  единый путь исключает рассинхрон.
- Источник данных для выборки — индексированный `engine.getCardsDueBy(now +
  learnAheadMs)` (range-запрос по `due`), а не полный скан. Использует **только**
  публичный API движка; не пишет в хранилище, не рассчитывает расписание.
- Детерминирован: при заданном `now` результат воспроизводим.
- `learnAheadMinutes` — **эргономический** knob (не когнитивная константа):
  не даёт «хвостовой» learning-карточке упереться в экран «Готово». Значимая
  для памяти дистанция живёт в FSRS review-интервалах.

**Границы сессии в web-клиенте (TASK_033).** `App` держит один экземпляр
`StudySession` на локальный календарный день: при первом возврате приложения
на передний план в новый день (и при выходе из сессии на Главную) создаётся
новый экземпляр — но никогда посреди сессии на экране (`app-lifecycle.ts`,
`shouldStartNewSession`). Иначе установленное на iPhone приложение, которое
не перезапускается, а «просыпается», переносило бы вчерашнее bury сестёр в
сегодня. Очередь и расход дневного лимита выводятся из Review Log, поэтому
новый экземпляр (как и перезапуск приложения) продолжает ту же очередь, а не
начинает независимую. Лимит применяется к новому экземпляру до показа Главной
(гейт `bootstrap` привязан к конкретному экземпляру).

Обоснование выделения в отдельный слой — [ADR-003](docs/adr/ADR-003-studysession-separation.md).

## 7. Scheduler (`packages/engine/src/scheduler.ts`, `fsrs-scheduler.ts`)

Граница алгоритма SRS. Интерфейс:

- `initialSchedule(now)` — состояние новой карты;
- `applyRating(card, rating, now)` — применить ответ;
- `preview(card, now)` — due для каждого рейтинга.

Единственная реализация сегодня — `FsrsScheduler` (обёртка над `ts-fsrs`,
`enable_fuzz: false`). Ядро общается с алгоритмом только через этот интерфейс,
поэтому FSRS заменяем без изменения хранилища, API движка или UI. Learning
steps (`1m`, `10m`) и переходы состояний обеспечивает сам FSRS.
Подробнее — [ADR-001](docs/adr/ADR-001-scheduler-abstraction.md).

## 8. EngineStore (`packages/engine/src/store.ts`)

Порт хранилища. Ядро зависит только от интерфейса; конкретные адаптеры — вне
логики планирования:

- `MemoryStore` (`memory-store.ts`) — референс-реализация для тестов;
- `DexieStore` (`apps/web/src/dexie-store.ts`) — IndexedDB для веба.

Методы: `getNote/getNotesByIds/listNotes/putNote/deleteNote`,
`getCard/putCard/deleteCard`, `listCards`, `listDueCards`, `appendReview`,
`listReviews`, `replaceAll` (атомарная замена всей коллекции — restore).
Reviews — append-only.
При удалении карты лог повторений намеренно сохраняется (история, статистика,
будущий re-fit параметров). `DexieStore` версионирует схему: `version(2)`
вводит таблицу `notes` и non-breaking `upgrade`-миграцию (синтетическая заметка
1:1 для каждой карты v1), без потери данных.

Индексы и батч-чтение (TASK_006): поле `due` индексировано (`cards: 'id, due,
deckId, noteId'`), поэтому `listDueCards(threshold)` — индексированный
range-запрос (`due <= threshold`, sorted), а не полный скан. `getNotesByIds(ids)`
— простой batch-примитив (bulk get по ключам, Dexie `bulkGet`), чтобы избежать
N+1 при построении списков; это остаётся хранилищем, а не query-построителем.
Миграция для TASK_006 не потребовалась — индекс `due` и таблица `notes` уже
существовали.

**Контракт порядка перечисления (TASK_014).** `listCards()` и `listCardViews()`
возвращают карты в едином **детерминированном, стабильном, тотальном** порядке.
**Нормативная спецификация:** по возрастанию `card.id` (лексикографически, как
порядок строковых ключей IndexedDB). Это **гарантия публичного контракта**,
обязательная для **всех** реализаций `EngineStore`, а не побочный эффект
адаптера. До TASK_014 порядок был не специфицирован (`MemoryStore` — порядок
вставки в `Map`; `DexieStore` — порядок первичного ключа), из-за чего идентичные
данные перечислялись по-разному, и это не ловилось тестами (length-only
`MockProvider`). Теперь `MemoryStore` явно сортирует по `id` на чтении, а
`DexieStore` использует `orderBy('id')` (не полагается на побочный эффект
`toArray()`). **Изменение нормативного порядка — breaking architectural change:
допускается только через отдельный ADR и отдельную задачу с явным изменением
публичного контракта Engine.** Область действия — **исключительно**
`listCards`/`listCardViews`; контракт не распространяется на `listDueCards`
(порядок по `due`) и не вводит Selection / Retrieval / Search / фильтрацию /
лимиты / окна. Номер INV-10 при этом **не присваивается** (как и в ADR-004).

## 9. Review Log

Иммутабельный, append-only журнал ответов пользователя — **source of truth**.
Каждый `Review` фиксирует: `rating`, `reviewedAt`, `stateBefore`, `stateAfter`,
`dueAfter`, `stability`, `difficulty`, `scheduledDays`. Scheduling-состояние на
карте (`SchedulingState`) — производный кэш.
Обоснование — [ADR-002](docs/adr/ADR-002-review-log-source-of-truth.md).

## 10. Replay Review Log → scheduling (реализовано, TASK_005)

Инвариант «Review Log — source of truth; scheduling — кэш» теперь **проверяемая
операция**, а не только декларация.

`LearningEngine.rebuildCardState(cardId)` восстанавливает `CardState` из одного
лишь лога повторений: seed = `scheduler.initialSchedule(createdAt)`, затем каждый
`Review` прогоняется через `scheduler.applyRating(card, rating, reviewedAt)` по
возрастанию времени (чистая утилита `replayCardState`, `packages/engine/src/replay.ts`).

**Схему менять не потребовалось.** Из-за детерминизма Scheduler для replay
достаточно `rating` + `reviewedAt` каждой записи (оба всегда хранились);
`reps/lapses/learningSteps/lastReview` **пересчитываются**, а не читаются —
поэтому новых полей в `Review` и миграции лога не нужно.

**Инвариант реализации (не ослаблять):** при построении seed используются
только идентификационные поля карты (`id`, `noteId`, `template`, `deckId`,
`createdAt`); scheduling-кэш (`due`, `state`, `scheduling`) как вход **полностью
игнорируется** и вычисляется заново. Операция чистая: лог не мутируется, ничего
не персистится (append-only цел).

Доказательство эквивалентности — в тестах: для разных историй `rebuildCardState`
== сохранённый кэш; отдельный тест **намеренно повреждает** `due`/`scheduling`
сохранённой карты и подтверждает, что реконструкция полностью восстанавливает
состояние **только из лога**.

Возможное развитие (не требуется сейчас): «repair»-вариант, который персистит
пересчитанное состояние (например, после смены/оптимизации параметров FSRS), и
оптимизация для очень длинных историй (сейчас replay — O(n) по числу повторений).

## 11. AI Layer (первый read-only consumer реализован, TASK_010)

Отдельный **независимый потребитель** публичного API `LearningEngine`,
равноправный с UI и StudySession (см. §1–2). Ограничения контракта:

- обращается к Engine только через публичный API, никогда — к хранилищу;
- Engine ничего не знает о существовании AI;
- «AI решает, когда/какую карточку показать» — отклоняется по умолчанию; это
  решение принадлежит детерминированному StudySession.

**Архитектурный принцип «Engine — единственный владелец данных».** AI Layer —
чистый **read-only** потребитель и **не создаёт собственного представления базы
знаний**: ни своего Storage, ни Search Engine, ни embeddings, ни индексов, ни
кэша. Все знания он получает **исключительно** из Engine через публичный API —
так же строго, как Engine не имеет доступа к сети/AI. Это **принцип, а не
нумерованный инвариант**: он может быть оформлен как INV-10 отдельной задачей,
если подтвердится последующими независимыми изменениями; в TASK_010 номер не
присваивается.

Реализация первого consumer — §11c (`packages/ai`). Дальнейшая ответственность
AI Layer (генерация карточек, объяснение ошибок, примеры, диалог,
персонализация; реальные LLM-провайдеры) — **направление** Phase 2+, ещё не
реализована.

## 11a. Anki-импорт (`packages/anki-import`, TASK_008)

Отдельный **пакет-потребитель** `@alsavi/anki-import` — импорт `.apkg`. **Не в
ядре**: парсинг чужого формата и его тяжёлые зависимости (zip/sqlite) не должны
попадать в `packages/engine` (которое обязано оставаться чистым — только
`ts-fsrs`, без сети/AI). Импортирует **только через публичный API**
(`engine.addNote`), в хранилище напрямую не пишет. Две независимые
ответственности (те же оси, что в ADR-003):

- **Anki Parser** (`parser.ts`): `.apkg` (zip → SQLite schema 11) → промежуточное
  представление `AnkiPackage`. Знает формат Anki, **не знает** о Note/Card ALSAVI.
  Библиотеки: `fflate` (unzip, фильтр — читает только collection DB, не медиа),
  `sql.js` (SQLite в WASM, оффлайн). Меняется, когда меняется формат Anki.
- **Anki Import Mapper** (`mapper.ts`): `AnkiPackage` → модель ALSAVI через
  `engine.addNote`. **Не знает** о zip/sqlite. Меняется, когда меняется модель.

Промежуточное представление — граница и точка тестирования: Mapper тестируется на
синтетических anki-объектах без реального файла; Parser — на самособранном мини-
`.apkg` (round-trip) и на реальном файле по `ALSAVI_TEST_APKG`.

Поддерживаемое подмножество (осознанно узкое; см. решения TASK_008): non-cloze
типы, `front=поле[0]`/`back=поле[1]` (лишние поля игнорируются), направления по
реальным `cards.ord` (0→forward, 1→reverse), поля очищаются до plain-text.
Импорт как **новые** карты (revlog не переносится). Неподдерживаемое —
пропускается со счётом в `ImportReport`, не роняя импорт. Импорт **добавляет** к
коллекции (никакого пересоздания БД).

## 11b. Backup / Restore (`packages/backup`, TASK_009)

Отдельный **пакет-потребитель** `@alsavi/backup` — полный самодостаточный снимок
коллекции и восстановление с заменой. **Storage-концерн**, а не memory-домен:
работает через **порт `EngineStore`** (`listNotes`/`listCards`/`listReviews` для
экспорта, `replaceAll` для восстановления), **публичный API `LearningEngine` НЕ
расширяется** (принцип №8). Модуль `serialize/validate` — чистый, тестируется в
node с `MemoryStore`.

- **Снимок** (JSON, `{format:'alsavi-backup', version, exportedAt, data:{notes,
  cards, reviews}}`) включает **полный Review Log** — source of truth (ADR-002),
  поэтому самодостаточен: `rebuildCardState` (TASK_005) воспроизводит состояние
  из лога. Scheduling-кэш тоже экспортируется — для точного, независимого от
  Scheduler восстановления.
- **Безопасный порядок восстановления (INV-9):** прочитать файл → **полная
  валидация** (структура + версия + ссылочная целостность: каждый `card.noteId`
  → существующая заметка, каждый `review.cardId` в `data.reviews` → карта, нет
  дублей id) → при успехе **явное подтверждение необратимой замены** (UI) →
  **атомарный** `store.replaceAll` (одна Dexie `rw`-транзакция: `clear`+`bulkAdd`).
  При провале валидации/несовместимой версии/сбое транзакции — прежние данные
  целы.
- **`replaceAll` принимает только провалидированные данные** — хранилище бэкап не
  валидирует.
- Необязательные поля заметки (TASK_023: `example`, `memo`, `tags`,
  `archivedAt`) проверяются по типу, если присутствуют; их отсутствие валидно;
  версия формата из-за них не менялась.
- **История удалённых карточек (TASK_027).** До TASK_023 `deleteCard` у карты с
  историей оставлял в Review Log повторения без карты (INV-4 — лог не чистится),
  и такие копии не восстанавливались. Теперь это история, а не мусор:
  - **экспорт** (`createBackup`/`exportBackup`) кладёт повторения без карты в
    `data.retiredReviews` и пишет **версию 2** — только если такие есть; иначе
    файл — версия 1, байт-в-байт прежний. `createBackup` возвращает и сводку
    `retired: {cards, reviews}` для уведомления в UI;
  - **версия 2:** `data.reviews` проверяется строго, как раньше (повторение без
    карты = повреждение); каждая запись `retiredReviews` — полноценное
    повторение (рейтинг, дата, состояния, числа), id уникален в обоих массивах,
    а карта **не** должна быть в файле (иначе повреждение). `retiredReviews` в
    файле версии 1 или его отсутствие в версии 2 — ошибка структуры;
  - **версия 1 (копии до TASK_027, решение владельца 3b):** объявить историю
    файл не мог, поэтому повторения без карты отличить от повреждённой ссылки
    нельзя. Они принимаются как история (`retired.legacy = true`), а решение —
    за пользователем: окно подтверждения восстановления называет их число и
    допускает, что файл повреждён. CLI `--db` (политика авто-подтверждения,
    §11d) принимает их без вопроса — снимок только для чтения;
  - **восстановление** возвращает обе части в **один** Review Log
    (`replaceAll`, `EngineStore` и ядро не менялись). История не ссылается на
    карту, поэтому не попадает ни в очереди, ни в FSRS, ни в `rebuildCardState`
    живых карт; статистика активности (§5b) учитывает её, как и до экспорта.
    `RestoreMeta.retired` есть только при наличии истории; повторный экспорт
    снова объявляет её в версии 2.
  - Тексты для пользователя — `apps/web/src/backup-messages.ts`: уведомление
    после экспорта, строка в подтверждении и итоге восстановления — только когда
    история есть.
- Deadlock TASK_007 **закрыт**: restore не зовёт сырой `deleteDatabase`, а
  заменяет строки транзакционно на живом соединении; managed close/reopen не
  нужен (транзакция делает его излишним — см. решение TASK_009).

## 11c. AI Layer (`packages/ai`, TASK_010 / TASK_011)

Отдельный **пакет-потребитель** `@alsavi/ai` — первый read-only consumer ядра.
Программная точка входа `AIService.answer(question): Promise<AIAnswer>`. **Не в
ядре**: `packages/engine` остаётся чистым (только `ts-fsrs`, без сети/AI).
Пакет **stateless**: ничего не хранит между вызовами, контекст пересобирается из
Engine на каждый `answer`.

Данные берутся **только** через публичный API `LearningEngine`
(`listCardViews` + `getStats`) — прямого доступа к `DexieStore`/внутренним
модулям Storage нет; публичный API ядра **не расширялся** (принцип №8). Одна
ответственность на модуль:

- **`ContextAssembler`** — собирает контекст из Engine (карты + статистика),
  сохраняя порядок Engine; **без** семантического ранжирования, сокращения или
  правки документов. Знает только про Engine.
- **`PromptBuilder`** — чистое построение текста prompt из готового контекста;
  не ищет, не вызывает модель.
- **`AnswerGenerator`** — генерация ответа через абстракцию `LLMProvider`; не
  знает о конкретной реализации провайдера.
- **`LLMProvider`** (`generate(prompt) → string`) — граница модели. Реализации:
  `MockProvider` (детерминированный, оффлайн — штатный провайдер тестов) и
  `OllamaProvider` (TASK_011) — реальный провайдер поверх локального Ollama
  (`POST {endpoint}/api/generate`, `stream:false`); endpoint и модель — только из
  конфигурации. Сам интерфейс `LLMProvider` не менялся — `OllamaProvider` лишь
  реализует его; tokenizer, подсчёт токенов, streaming, второй провайдер не
  вводятся.
- **`AIService`** — только оркестрация: `ContextAssembler` → `PromptBuilder` →
  Context Budget Guard → `AnswerGenerator` → `AIAnswer`.

`AIAnswer` — `{ readonly answer: string; readonly sources?: readonly string[] }`;
`sources` зарезервировано под будущие citations и не заполняется (объект, а не
голая строка — чтобы расширять без ломающего изменения API).

**Context Budget Guard (TASK_011).** `AIService.answer` перед вызовом провайдера
— т.е. **до любого HTTP** — сравнивает длину итогового prompt (в **символах**) с
`contextBudgetChars` (обязательное поле `AIServiceOptions`); при превышении бросает
`ContextBudgetExceededError { actualChars, budgetChars }`, провайдер не
вызывается. Guard живёт inline в `AIService` (одна проверка; отдельной
абстракции не заведено — принцип простоты). **Context Budget ≠ Model Window:**
это сознательный consumer-side лимит на объём отправляемого текста в символах, а
не токеновое окно модели — токены AI Layer не считает и не токенизирует.

Границы enforced тестами (`packages/ai/test`, симметрично `layer boundary`
ядра): ни один файл Engine не импортирует из `ai`; ни один файл `ai` не
импортирует `DexieStore`/внутренние модули Storage — доступ к данным только
через публичный API. Если публичного API окажется недостаточно для
**необходимого** контекста — по правилу задачи реализация останавливается и
вопрос выносится основателю, а не решается своим индексом/поиском/кэшем.

## 11d. CLI (`apps/cli`, TASK_012 / TASK_013)

**Первая законченная пользовательская точка входа ALSAVI** — команда `ask`
(`apps/cli`, `@alsavi/cli`). Это `apps/*` (приложение-потребитель), не
библиотека. Полный путь: `CLI → AIService.answer() → Engine → OllamaProvider →
модель → stdout`. **Никакого нового транспортного слоя** (HTTP/REST/GraphQL/
WebSocket/IPC/daemon) — CLI вызывает `AIService.answer()` прямо в Node-процессе.

- **Композиция, без бизнес-логики.** CLI = ручной разбор `process.argv` (без
  CLI-фреймворков) → создание `AIService`/`OllamaProvider` → `answer()` → вывод
  ответа → код возврата. Разбор аргументов вынесен в чистый `args.ts`; вся
  оркестрация — в `run(argv, io): Promise<exitCode>` (пишет через инъектируемые
  stdout/stderr, поэтому тестируется без обращения к process-потокам); `main.ts`
  — тонкий bin-entry.
- **Конфигурация только через аргументы** (`--model`, `--context-budget`
  обязательны; `--endpoint` опционален), без dotenv/env/config-файлов.
  `--context-budget` маппится в обязательный `contextBudgetChars`
  (`AIServiceOptions`).
- **Дефолт endpoint — политика CLI, не провайдера.** При отсутствии
  `--endpoint` CLI передаёт в `OllamaProvider` `http://127.0.0.1:11434`. Сам
  `OllamaProvider` дефолта не содержит (TASK_011) — политика по умолчанию живёт
  у потребителя.
- **Требуемый `AIServiceOptions.engine`** удовлетворяется композицией: CLI
  создаёт in-memory движок `new LearningEngine(new MemoryStore())`. Поэтому CLI
  зависит от `@alsavi/ai`, `@alsavi/engine` и `@alsavi/backup` (только чтобы
  построить и наполнить требуемый движок). **AI Layer, Engine, backup и их
  публичные API не изменялись.**
- **Источник данных — снимок реальной базы через `--db <path>` (TASK_013).**
  Без `--db` — пустой `MemoryStore` (поведение TASK_012). С `--db` CLI читает
  экспортированный backup-файл (`node:fs`, UTF-8) и наполняет `MemoryStore`
  существующим механизмом восстановления: `await importBackup(store, text)`
  (сам валидирует через `parseBackup`, бросает `BackupError` на невалидном
  входе) → `new LearningEngine(store)`. CLI **использует** этот механизм, не
  дублирует и не парсит backup вручную. **Мост `web → file → CLI`:** реальные
  данные живут в браузерном IndexedDB (`DexieStore`), недоступном Node; ручной
  экспорт из web (`exportBackup` → JSON) — единственный путь в Node. CLI
  отвечает **по снимку на момент экспорта**, не по live-базе; изменения в web
  после выгрузки в снимок не попадают — осознанная граница первого сценария
  (живая синхронизация/общий Node-стор вне рамок). Ошибки загрузки (файл не
  найден/нечитаем, невалидный backup) → stderr + код ≠ 0, движок/`AIService` не
  строятся.
- Чтение файла инъектируется в `run(argv, io, deps?)` (`deps.readFile`, по
  умолчанию `node:fs/promises`) — тесты подменяют reader, не касаясь диска.
- **Ошибки → stderr + код возврата ≠ 0:** неверные аргументы (AIService не
  создаётся), `ContextBudgetExceededError` (показываются `actualChars`/
  `budgetChars`), runtime-ошибки (Ollama недоступна/ECONNREFUSED —
  пробрасываются как есть; без retry/автозапуска/подмены endpoint). Успех →
  ровно текст ответа модели в stdout, код `0`.
- **Тесты (`apps/cli/test`)**: разбор аргументов, маппинг флагов (вкл. `--db`),
  коды возврата, дефолт endpoint (`http://127.0.0.1:11434`), обработка ошибок;
  `--db` — валидный снимок (наполнение `MemoryStore`, ответ по непустой базе,
  провайдер вызван один раз), несуществующий файл и невалидный backup (код ≠ 0,
  провайдер не вызван), и сохранение поведения без `--db`. Весь HTTP мокируется
  (`vi.stubGlobal('fetch', …)`), `fs` — через инъектированный reader — ни один
  тест не требует ни Ollama, ни реального файла; CI детерминирован.

## 11e. PWA: офлайн и обновление (`apps/web/public/sw.js`, `registerSW.ts`)

Service worker кэширует **только оболочку приложения** (документ, бандлы,
манифест, иконки); данные обучения живут только в IndexedDB и сервис-воркеру
недоступны. Кэш версионируется SHA коммита (`alsavi-shell-<sha>`), при
активации удаляются только старые кэши с этим префиксом; IndexedDB не
удаляется никогда.

- **Установка** кэширует оболочку запросами `cache: 'reload'` (TASK_033), мимо
  HTTP-кэша браузера: иначе в первые минуты после деплоя (GitHub Pages отдаёт
  `index.html` с `max-age=600`) новый кэш мог получить старый `index.html` с
  новыми бандлами — и офлайн-старт показал бы пустой экран. Неудачная
  установка оставляет прежнюю версию в работе.
- **Навигация** — сначала сеть, офлайн — закэшированная оболочка; бандлы —
  stale-while-revalidate.
- **Обновление открытого приложения (TASK_033).** При каждом возврате на
  передний план — `registration.update()`. Новая версия ставится и берёт
  управление сама (`skipWaiting` + `clients.claim`); открытая страница
  продолжает работать на уже загруженном коде, а UI показывает «Доступна новая
  версия ALSAVI · Обновить» (не во время сессии и тренировки). Сам по себе
  интерфейс не перезагружается: перезагрузка потеряла бы набранный текст
  карточки. Первая установка обновлением не считается.
- Поведение покрыто `sw-runtime.test.ts` (настоящий `sw.js` в песочнице с
  фейковыми `caches`/`fetch`) и `sw-update.test.ts`.

## 12. Future Architecture (направление, не контракт)

Ниже — стратегические направления из конституции/Roadmap. **Интерфейсы заранее
не проектируются** (режимы Voice/Reading/Exam, мультиколоды и т.п. — не имеют
согласованных контрактов и не должны их получать до своей задачи):

- AI Layer сверх первого read-only consumer (§11c): генерация карточек,
  диалог, объяснение ошибок, реальные LLM-провайдеры — Phase 2+.
- Экспорт/импорт/резервное копирование данных пользователя.
- Синхронизация между устройствами; импорт Anki `.apkg`.
- Дополнительные учебные режимы — как **новые независимые потребители**
  ядра / стратегии StudySession, а не как ветки внутри ядра.
- Interleaving new/learning-приоритета — как политика StudySession (дневной
  лимит новых карт уже реализован, см. §6, TASK_020).
- `max-reviews/day` и undo (`M1`) — остаются будущими задачами; undo требует
  отдельного ADR (затрагивает append-only-инвариант Review Log, INV-4).

Всё перечисленное — направление, а не обязательство и не проектная спецификация.

- ARCHITECTURE.md обновляется, когда меняется **фактическая** архитектура
  (новый слой/потребитель, новый порт, изменение инварианта), — в том же PR,

  противоречий; не переписывать ради стиля.
