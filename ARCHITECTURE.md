# ARCHITECTURE — ALSAVI

Источник архитектурной истины проекта. Терминология и принципы наследуются из
[`PROJECT_CONSTITUTION.md`](PROJECT_CONSTITUTION.md) (commit `00972bb`), раздел
CORE ARCHITECTURE. Этот документ описывает **фактическое** состояние кода, а не
планы. Разработчику, впервые открывшему проект, стоит читать вместе с
[`ENGINE.md`](ENGINE.md) и решениями в [`docs/adr/`](docs/adr/).

> Статус на момент написания: Phase 1 (Learning Engine + web MVP), после
> TASK_001 (in-session Learning Steps через StudySession). AI Layer ещё не
> реализован.

---

## 1. Общая модель

ALSAVI построен вокруг одного детерминированного ядра памяти —
`LearningEngine` — и набора **независимых потребителей** его публичного API.

**Ключевая формулировка (из конституции, обязательна во всех документах):**
AI Layer — **не последовательный слой, через который проходит память**, а
**отдельный потребитель публичного API `LearningEngine`, равноправный с UI и
StudySession**. Любой потребитель (UI, StudySession, AI Layer) обращается к
Engine **только через публичный интерфейс** — никогда напрямую к хранилищу.

Потребители **не выстроены в цепочку** `Engine → StudySession → UI → AI`. Каждый
обращается к ядру самостоятельно. StudySession и AI Layer — параллельные
потребители одного ядра, а не звенья одной цепи.

## 2. Диаграмма

```
        Потребители публичного API LearningEngine
        (независимы; ни один не проходит «сквозь» другой)

    ┌──────────────┐   ┌──────────────────┐   ┌────────────────────────┐
    │   UI (web)   │   │   StudySession   │   │   AI Layer (будущее,   │
    │ ReviewSession│   │  (поток сессии:  │   │   ещё НЕ реализован)   │
    │  CardManager │   │  какую карточку  │   │  генерация карточек,   │
    │              │   │  показать далее) │   │  разбор ошибок, диалог │
    └──────┬───────┘   └────────┬─────────┘   └───────────┬────────────┘
           │                    │                         │
           │            только публичный API              │
           └────────────────────┼─────────────────────────┘
                                 ▼
                  ╔═══════════════════════════════╗
                  ║        LearningEngine          ║
                  ║  детерминированное ядро памяти  ║
                  ║  (addCard, review, getDueCards, ║
                  ║   previewIntervals, getStats…)  ║
                  ╚═══════┬───────────────┬════════╝
                          │               │
                 Scheduler│               │EngineStore
                (алгоритм SRS,            │(порт хранилища,
                 заменяем)                │ заменяем)
                          ▼               ▼
                   FsrsScheduler   MemoryStore (тесты)
                   (ts-fsrs)       DexieStore (web/IndexedDB)
```

Примечание: UI фактически **композирует** StudySession (спрашивает у него
«какую карточку показать») и одновременно сам вызывает Engine (записать ответ,
превью интервалов, статистика). Но StudySession **никогда** не стоит между AI и
ядром — каждый потребитель говорит с ядром напрямую. Именно это и означает
«параллельные потребители».

## 3. Architecture Principles

1. **Детерминированное ядро.** `LearningEngine` и его `Scheduler` не содержат
   случайности (FSRS fuzz выключен). Одинаковая история → одинаковое расписание.
2. **Автономность ядра.** Ни одного импорта сети или AI в `packages/engine`.
   Проверяется тестом `layer boundary`.
3. **Доступ только через публичный API.** Потребители не читают и не пишут в
   хранилище напрямую.
4. **Обратимость через порты.** Алгоритм за `Scheduler`, хранилище за
   `EngineStore`. Реализацию можно заменить, не трогая контракт.
5. **Разделение осей изменения (SRP).** Расчёт памяти (Engine) и поток учебной
   сессии (StudySession) меняются по разным причинам и живут раздельно
   (см. [ADR-003](docs/adr/ADR-003-studysession-separation.md)).
6. **Локальность и скорость.** Всё, что можно, считается локально и мгновенно.
7. **Простота прежде архитектурной чистоты** (порядок приоритетов конституции),
   кроме границы «Engine ↔ потребители», закладываемой с первого дня.
8. **Минимальный публичный API ядра.** `LearningEngine` предоставляет минимальный
   публичный API, необходимый существующим потребителям; он не стремится быть
   универсальным query-слоем. Политика выбора, интерпретации и порядка обработки
   данных остаётся ответственностью потребителей, таких как `StudySession`.

## 4. Architecture Invariants

Инварианты, которые нельзя нарушать без отдельного обсуждения контракта:

- **INV-1.** `packages/engine` не импортирует сеть/AI (enforced: тест
  `layer boundary` в `engine.test.ts`).
- **INV-2.** Планирование детерминировано; изменение планирования допускается
  только с тестом на регрессию расписания.
- **INV-3.** Редактирование контента (`updateNoteContent`) **никогда** не
  изменяет scheduling-состояние (enforced тестом).
- **INV-4.** Review Log — append-only, source of truth. Scheduling-состояние
  карточки — кэш.
- **INV-5.** `CardState` фиксируется в каждом `Review` (`stateBefore`/
  `stateAfter`) и воспроизводим из лога через `rebuildCardState` (см. §10).
- **INV-6.** StudySession и AI Layer обращаются к ядру только через публичный
  API; StudySession не рассчитывает расписание и не пишет в хранилище.
- **INV-7.** Если AI Layer недоступен — Engine и StudySession работают в полном
  объёме.
- **INV-8.** Контент принадлежит `Note` (единственный источник истины); `Card`
  не хранит `front/back`, а рендерит их из заметки. Редактирование контента
  никогда не изменяет scheduling (обновлённая форма INV-3).

## 5. LearningEngine (`packages/engine/src/engine.ts`)

Детерминированное ядро памяти и единственная точка входа к картам и расписанию.
Публичный API:

| Метод | Назначение |
|---|---|
| `addNote({front, back, directions?})` | создать заметку + 1..N карт (due сразу, `new`) |
| `addCard({front, back, deckId?})` | сахар: одна forward-карта (Note 1:1) |
| `updateNoteContent(noteId, {front, back})` | правка контента заметки → все сёстры; scheduling не трогается |
| `updateCardContent(id, …)` | `@deprecated` мостик: только forward без сестёр, иначе ошибка |
| `deleteCard(id)` | удалить карту (+ заметку, если последняя); лог сохраняется |
| `deleteNote(id)` | удалить заметку и её карты; лог сохраняется |
| `getNote(id)` / `getCard(id)` / `listCards()` | чтение |
| `getCardView(id)` / `listCardViews()` | карта(ы) с контентом из заметки (список — batch-загрузка заметок) |
| `getDueCards(limit?)` | карты с `due <= now`, по возрастанию `due` |
| `getCardsDueBy(threshold)` | индексированный факт-запрос `due <= threshold` (для learn-ahead StudySession) |
| `review(cardId, rating)` | записать ответ: пересчёт + append в Review Log |
| `previewIntervals(cardId)` | due-даты для каждого рейтинга (для кнопок) |
| `getStats()` | totalCards, newCards, dueNow, reviewsToday, accuracy, streak |

Зависимости внедряются: `store: EngineStore`, `scheduler?` (по умолчанию
`FsrsScheduler`), `now?()`, `newId?()` — часы и генератор id инъектируются ради
детерминизма/тестируемости.

## 5a. Note → Card (модель контента)

`Note` (`packages/engine/src/types.ts`) — **единственный источник истины для
контента**. Одна заметка порождает одну или несколько карт (`forward`/`reverse`
через `addNote({directions})`). `Card` **не хранит** свой `front/back`: они
вычисляются из заметки чистой функцией `renderCard(card, note)`
(`render.ts`). Следствия:

- редактирование `updateNoteContent` мгновенно отражается на всех картах-сёстрах
  — дрейф контента структурно невозможен;
- у каждой карты заметки **своё независимое** планирование и `state` (Scheduler и
  Review Log работают пер-карта — Note им невидим);
- UI берёт готовый контент через `getCardView`/`listCardViews` (рендер — в ядре).

`Deck` (пока строка `deckId` на карте) и `CardType` (система шаблонов) как
сущности **не** реализованы: `template` — ограниченный enum `forward|reverse`.
Модель допускает их добавление позже без ре-миграции Note.

## 6. StudySession (`packages/engine/src/study-session.ts`)

**Детерминированный слой учебного потока.** Отвечает за то, *какую карточку
показать следующей*, — но не за то, *как считать память*.

- Публичные методы: `nextCard()`, `dueCount()`, `answer(cardId, rating)`.
- Политика выборки: сначала реально due-карточки (`due <= now`, порядок по
  `due`, tie-break по `id`); иначе — learning/relearning-карточка в окне
  learn-ahead (`learnAheadMinutes`, по умолчанию 20). Не-due review/new карты
  досрочно не показываются.
- **Bury siblings:** после ответа сёстры отвеченной карты (та же `noteId`, кроме
  самой карты) не показываются до конца сессии; `dueCount()` их исключает
  (инвариант TASK_002 сохранён); единственная оставшаяся погребённая сестра не
  показывается — сессия завершается. Состояние bury — эфемерные in-memory `Set`
  на экземпляре, **не персистится**; границы сессии = время жизни экземпляра
  `StudySession`, а не календарное время.
- `answer()` — **оркестратор**: делегирует запись в `engine.review()` (единственный
  writer в Review Log/scheduling/CardState) и обновляет только своё bury-состояние;
  единый путь исключает рассинхрон.
- Источник данных для выборки — индексированный `engine.getCardsDueBy(now +
  learnAheadMs)` (range-запрос по `due`), а не полный скан. Использует **только**
  публичный API движка; не пишет в хранилище, не рассчитывает расписание.
- Детерминирован: при заданном `now` результат воспроизводим.
- `learnAheadMinutes` — **эргономический** knob (не когнитивная константа):
  не даёт «хвостовой» learning-карточке упереться в экран «Готово». Значимая
  для памяти дистанция живёт в FSRS review-интервалах.

Обоснование выделения в отдельный слой — [ADR-003](docs/adr/ADR-003-studysession-separation.md).

## 7. Scheduler (`packages/engine/src/scheduler.ts`, `fsrs-scheduler.ts`)

Граница алгоритма SRS. Интерфейс:

- `initialSchedule(now)` — состояние новой карты;
- `applyRating(card, rating, now)` — применить ответ;
- `preview(card, now)` — due для каждого рейтинга.

Единственная реализация сегодня — `FsrsScheduler` (обёртка над `ts-fsrs`,
`enable_fuzz: false`). Ядро общается с алгоритмом только через этот интерфейс,
поэтому FSRS заменяем без изменения хранилища, API движка или UI. Learning
steps (`1m`, `10m`) и переходы состояний обеспечивает сам FSRS.
Подробнее — [ADR-001](docs/adr/ADR-001-scheduler-abstraction.md).

## 8. EngineStore (`packages/engine/src/store.ts`)

Порт хранилища. Ядро зависит только от интерфейса; конкретные адаптеры — вне
логики планирования:

- `MemoryStore` (`memory-store.ts`) — референс-реализация для тестов;
- `DexieStore` (`apps/web/src/dexie-store.ts`) — IndexedDB для веба.

Методы: `getNote/getNotesByIds/putNote/deleteNote`, `getCard/putCard/deleteCard`,
`listCards`, `listDueCards`, `appendReview`, `listReviews`. Reviews — append-only.
При удалении карты лог повторений намеренно сохраняется (история, статистика,
будущий re-fit параметров). `DexieStore` версионирует схему: `version(2)`
вводит таблицу `notes` и non-breaking `upgrade`-миграцию (синтетическая заметка
1:1 для каждой карты v1), без потери данных.

Индексы и батч-чтение (TASK_006): поле `due` индексировано (`cards: 'id, due,
deckId, noteId'`), поэтому `listDueCards(threshold)` — индексированный
range-запрос (`due <= threshold`, sorted), а не полный скан. `getNotesByIds(ids)`
— простой batch-примитив (bulk get по ключам, Dexie `bulkGet`), чтобы избежать
N+1 при построении списков; это остаётся хранилищем, а не query-построителем.
Миграция для TASK_006 не потребовалась — индекс `due` и таблица `notes` уже
существовали.

## 9. Review Log

Иммутабельный, append-only журнал ответов пользователя — **source of truth**.
Каждый `Review` фиксирует: `rating`, `reviewedAt`, `stateBefore`, `stateAfter`,
`dueAfter`, `stability`, `difficulty`, `scheduledDays`. Scheduling-состояние на
карте (`SchedulingState`) — производный кэш.
Обоснование — [ADR-002](docs/adr/ADR-002-review-log-source-of-truth.md).

## 10. Replay Review Log → scheduling (реализовано, TASK_005)

Инвариант «Review Log — source of truth; scheduling — кэш» теперь **проверяемая
операция**, а не только декларация.

`LearningEngine.rebuildCardState(cardId)` восстанавливает `CardState` из одного
лишь лога повторений: seed = `scheduler.initialSchedule(createdAt)`, затем каждый
`Review` прогоняется через `scheduler.applyRating(card, rating, reviewedAt)` по
возрастанию времени (чистая утилита `replayCardState`, `packages/engine/src/replay.ts`).

**Схему менять не потребовалось.** Из-за детерминизма Scheduler для replay
достаточно `rating` + `reviewedAt` каждой записи (оба всегда хранились);
`reps/lapses/learningSteps/lastReview` **пересчитываются**, а не читаются —
поэтому новых полей в `Review` и миграции лога не нужно.

**Инвариант реализации (не ослаблять):** при построении seed используются
только идентификационные поля карты (`id`, `noteId`, `template`, `deckId`,
`createdAt`); scheduling-кэш (`due`, `state`, `scheduling`) как вход **полностью
игнорируется** и вычисляется заново. Операция чистая: лог не мутируется, ничего
не персистится (append-only цел).

Доказательство эквивалентности — в тестах: для разных историй `rebuildCardState`
== сохранённый кэш; отдельный тест **намеренно повреждает** `due`/`scheduling`
сохранённой карты и подтверждает, что реконструкция полностью восстанавливает
состояние **только из лога**.

Возможное развитие (не требуется сейчас): «repair»-вариант, который персистит
пересчитанное состояние (например, после смены/оптимизации параметров FSRS), и
оптимизация для очень длинных историй (сейчас replay — O(n) по числу повторений).

## 11. AI Layer (будущее, ещё не реализован)

Отдельный **независимый потребитель** публичного API `LearningEngine`,
равноправный с UI и StudySession (см. §1–2). Планируемая ответственность
(Phase 2+, по конституции): генерация карточек, объяснение ошибок, примеры,
диалог, персонализация. Ограничения контракта:

- обращается к Engine только через публичный API, никогда — к хранилищу;
- Engine ничего не знает о существовании AI;
- «AI решает, когда/какую карточку показать» — отклоняется по умолчанию; это
  решение принадлежит детерминированному StudySession.

Кода AI пока нет — раздел описывает **направление**, не контракт.

## 12. Future Architecture (направление, не контракт)

Ниже — стратегические направления из конституции/Roadmap. **Интерфейсы заранее
не проектируются** (режимы Voice/Reading/Exam, мультиколоды и т.п. — не имеют
согласованных контрактов и не должны их получать до своей задачи):

- AI Layer как первый независимый потребитель поверх ядра (Phase 2).
- Экспорт/импорт/резервное копирование данных пользователя.
- Синхронизация между устройствами; импорт Anki `.apkg`.
- Дополнительные учебные режимы — как **новые независимые потребители**
  ядра / стратегии StudySession, а не как ветки внутри ядра.
- Дневные лимиты новых карт и interleaving — как политика StudySession.

Всё перечисленное — направление, а не обязательство и не проектная спецификация.

## 13. Правила обновления этого документа

- ARCHITECTURE.md обновляется, когда меняется **фактическая** архитектура
  (новый слой/потребитель, новый порт, изменение инварианта), — в том же PR,
  что и код.
- Терминология AI Layer / StudySession должна оставаться согласованной с
  `PROJECT_CONSTITUTION.md` (§1). При конфликте первичен документ основателя.
- Не описывать нереализованное как реализованное; будущее — только в §11–12.
- Изменять только то, что нужно для корректности/полноты/устранения
  противоречий; не переписывать ради стиля.
- Архитектурные **решения** фиксируются как ADR в [`docs/adr/`](docs/adr/);
  ARCHITECTURE.md ссылается на них, а не дублирует.
