# ADR-005 — Application Services Layer

**Статус:** Proposed · Roadmap «ALSAVI Beta — Anki Replacement», milestone M0

> Опирается на принятый документ планирования
> [`docs/ROADMAP_ALSAVI_BETA.md`](../ROADMAP_ALSAVI_BETA.md) (§1, M0) и
> **обобщает** [ADR-003](ADR-003-studysession-separation.md) (выделение
> `StudySession`) до явного слоя приложения. Не проектирует внутренние
> интерфейсы конкретных сервисов — это предмет отдельных реализационных задач,
> открываемых, когда соответствующий milestone входит в scope.

## Context

Roadmap ALSAVI Beta вводит слой **Application Services** как оркестрационный
ярус между UI и ядром. Причина — фактическое состояние кода и два горизонта
ALSAVI (самостоятельное приложение и будущий модуль A-Lex Core).

**Что есть сегодня (наблюдение из репозитория).** Бизнес-оркестрация живёт
**внутри React-компонентов** (`apps/web`): импорт `.apkg`, export/restore
резервной копии, обновление статистики, склейка `StudySession` — всё это в
`CardManager.tsx` и `App.tsx`. Следствия:

- логика **заперта в UI** — её нельзя переиспользовать в будущих оболочках
  (mobile, CLI уже существует отдельно, встраивание в A-Lex Core) без переноса
  React;
- она **непроверяема без DOM** — сценарии тестируются только через UI;
- каждая новая фича roadmap (M2 browser/editor, M4 stats), реализованная «как
  сейчас», **наращивает связанность** в компонентах.

При этом *прото-сервисы* уже существуют как независимые потребители публичного
API ядра: `StudySession` (`packages/engine`), `AIService` (`packages/ai`),
`@alsavi/backup`, `@alsavi/anki-import`. Но они **не организованы в связный
прикладной ярус**, а оркестрация, которая их сшивает, лежит в UI.

**Требования, определяющие рамку решения:**

- **Конституция, приоритет конфликтов:** работающий продукт → простота →
  качество кода → архитектурная чистота. Но единственное явное исключение —
  границу «Engine ↔ потребители» закладывают **с первого дня**, т.к. дорого
  добавлять задним числом. Этот ADR распространяет ту же логику на границу
  «UI ↔ Services».
- **Инварианты ядра (не ослаблять):** потребители обращаются к данным памяти
  **только через публичный API `LearningEngine`**, никогда напрямую в Storage
  (INV-6); Engine — единственный владелец **данных памяти**; **минимальный
  публичный API ядра** (принцип №8); ядро автономно от сети/AI (INV-1/2).
- **ADR-003** уже выделил **один** компонент (`StudySession`) как отдельный
  детерминированный слой потока сессии — параллельный потребитель публичного API,
  а не звено цепи. Настоящий ADR **обобщает** этот приём до явного яруса, не
  отменяя ADR-003.
- **Экосистема A-Lex Core** (Health, Finance, Ministry): ALSAVI должен быть и
  самостоятельным приложением, и встраиваемым модулем → нужен
  **платформо-независимый** оркестрационный ярус, переиспользуемый разными
  оболочками.

## Problem

Где живёт оркестрация use-case'ов — размазанной по каждой UI-оболочке, или в
выделенном платформо-независимом слое Services между UI и публичным API ядра?

Вопрос об **ответственности и её месте**, а не о сигнатурах конкретных сервисов.

## Options

**Вариант A — статус-кво: оркестрация в UI-оболочках.** Каждая оболочка (web,
будущий mobile, CLI, встраивание в A-Lex) сама сшивает Engine + прото-сервисы.
- *Плюсы:* ничего не надо вводить сегодня; максимально просто прямо сейчас.
- *Минусы:* оркестрация **дублируется на оболочку**; логика заперта в React;
  непроверяема без DOM; интеграция в A-Lex Core вынуждена переизобрести всё
  заново; связанность растёт с каждой фичей. Смешивает ось «подача/презентация»
  с осью «оркестрация приложения».

**Вариант B — слой Application Services: платформо-независимые пакеты use-case'ов
между UI и ядром.** UI становится **только презентацией**; сервисы оркеструют
публичный API ядра и прото-потребителей (`StudySession`, backup, import, AI).
- *Плюсы:* переиспользование во всех оболочках и в A-Lex Core; headless-
  тестируемость; UI упрощается; связанность локализуется (фичи строятся в
  сервисах, не в компонентах); инварианты ядра сохраняются полностью;
  согласовано с ADR-003 (обобщение) и с исключением конституции про границу «с
  первого дня».
- *Минусы:* дополнительный ярус + разовый рефакторинг извлечения существующей
  оркестрации из UI (должен быть behavior-preserving и покрыт тестами).

**Вариант C — «толстое ядро»: перенести оркестрацию в `LearningEngine`.**
- *Отклонён:* нарушает принцип №8 (минимальный публичный API) и SRP (ADR-003);
  смешивает ось памяти с осью приложения/презентации; воссоздаёт ровно то, что
  ADR-003 разделил. Тесты ядра смешивают корректность расписания и сценарии
  приложения.

**Вариант D — единый «god-service» / только фасад.**
- *Отклонён:* монолитный сервис возвращает связанность через дверь, которую ярус
  должен закрыть. Предпочтительнее **feature-aligned вертикальные сервисы** с
  одной ответственностью каждый.

## Decision

Выбран **Вариант B**. Вводится явный **слой Application Services** —
**платформо-независимые** (без React/DOM) пакеты, владеющие оркестрацией
use-case'ов, между UI и публичным API `LearningEngine`.

- **Feature-aligned вертикальные сервисы**, одна ответственность на сервис:
  `CardService`, `DeckService`, `StudyService`, `StatsService`, `ImportService`,
  `BackupService`, `SettingsService`. (Точные интерфейсы — предмет задач
  соответствующих milestone'ов, не этого ADR.)
- Сервисы соблюдают тот же контракт, что и все потребители: **данные памяти —
  только через публичный API ядра, никогда напрямую в Storage** (INV-6). Ядро
  остаётся **не осведомлённым** о слое Services — ровно как оно не осведомлено об
  AI.
- **`StudySession` поглощается** как первый/референсный экземпляр яруса (лежит в
  основе `StudyService`); решение ADR-003 остаётся в силе, настоящий ADR его
  обобщает. `AIService` и пакеты `@alsavi/backup`/`@alsavi/anki-import`
  признаются уже существующими сервисами этого яруса.
- **Оркестрация извлекается из UI** (импорт, backup/restore, обновление
  статистики, склейка сессии) в сервисы — **behavior-preserving, покрыто
  тестами**. Это **локальное улучшение, а не переписывание** (конституция: не
  переписывай готовое, если можно улучшить локально).
- **Инварианты и код ядра не тронуты**; регрессия расписания невозможна по
  построению (Engine не меняется).

Это решение об **ответственности и границе**, а не о механизме конкретных
сервисов.

### Что этот ADR сознательно НЕ решает (границы scope)

- **Границу «данные памяти vs данные приложения» и `AppDataRepository`** (где
  живут настройки, метаданные колод, prefs) — отдельный ADR; до него сервисы
  берут данные памяти только через публичный API ядра.
- **Module Contract (`AlsaviModule`) и Domain Events** — интеграционный шов
  A-Lex Core — отдельный ADR.
- **Семантику Undo**, **`CardQuery` vs retrieval (ADR-004)**, **extensible note
  model** — отдельные ADR своих milestone'ов.
- Точную раскладку пакетов сверх принципа «платформо-независимо,
  feature-aligned».

## Consequences

**Плюсы:**
- Переиспользование во всех оболочках (web/mobile/CLI) и в A-Lex Core: одна
  оркестрация, а не по копии на оболочку.
- **Headless-тестируемость** прикладных сценариев (без DOM).
- UI сводится к презентации; связанность локализуется — фичи roadmap строятся в
  сервисах, а не в компонентах.
- Все инварианты ядра сохранены; граница «доступ к памяти только через публичный
  API» усилена, а не размыта.
- Согласовано с ADR-003 (прямое обобщение) и CORE ARCHITECTURE конституции
  (параллельные независимые потребители), а также с принципом
  feature-oriented модульности.

**Минусы / цена:**
- Дополнительный ярус + разовый рефакторинг извлечения существующей UI-
  оркестрации (обязателен behavior-preserving и покрытый тестами; иначе риск
  регресса поведения при переносе).
- Риск **преждевременной абстракции**: сервис, созданный до того, как его фича
  вошла в scope, или сервис, лишь пробрасывающий вызов к ядру, добавляет
  сложность без ценности. Митигируется правилом: **сервис заводится, когда его
  фича входит в scope**, и оправдывается реальной оркестрацией, а не проксированием.

**Границы:** сервисы — потребители; их можно реорганизовывать. Несущая часть —
**контракт**: `UI → Services → публичный API Engine`; никакого прямого доступа в
Storage; ядро не меняется и не осведомлено о слое. Изменение самого контракта —
новый ADR, замещающий этот, а не правка данного (ADR иммутабелен по смыслу).

**Статус-переход:** решение оформлено как **Proposed**. При реализации milestone
M0 (материализация слоя и извлечение оркестрации) статус может быть переведён в
Accepted либо замещён уточняющим ADR, если реализация вскроет расхождение.
