# ADR-003 — StudySession separation from LearningEngine

**Статус:** Accepted · TASK_001

## Context

TASK_001 требовал полноценные Learning Steps: после ответа «Again» карточка
должна возвращаться в **текущую** учебную сессию по своему короткому шагу, не
дожидаясь перезапуска приложения.

Анализ показал: сами learning steps FSRS уже считал (Again → `learning`,
`due≈+1m`). Разрыв был не в алгоритме, а в **слое сессии**: UI брал только
`getDueCards(now)` (карты с `due <= now`), поэтому карта, перепланированная на
`now+1m`, из сессии исчезала. Нужен был компонент, решающий «какую карту
показать следующей» с учётом learn-ahead.

Ключевой вопрос: где живёт это решение — внутри `LearningEngine` или в отдельном
компоненте? В основе — **разные оси изменения** (SRP):

- `LearningEngine` меняется по причинам **памяти**: алгоритм SRS, модель карты,
  хранилище.
- Поток сессии меняется по причинам **подачи**: порядок, learn-ahead, будущие
  дневные лимиты, interleaving, режимы, влияние AI на порядок.

Смешение этих осей в одном классе — второй повод менять ядро памяти, то есть
нарушение SRP и размытие границы «расписание ↔ поток».

## Options

- **Вариант A — метод `getNextCard()` на `LearningEngine`.** Быстро сегодня, но
  тащит session-политику в детерминированное ядро памяти. С ростом политики
  (лимиты, режимы) ядро обрастает ветками или режимы идут мимо метода — SRP-
  запах усиливается. Тесты ядра смешивают корректность расписания и сценарии
  сессии.
- **Вариант B-minimal — отдельный маленький `StudySession` поверх публичного
  API ядра.** Реализует только сегодняшнюю нужду (порядок + learn-ahead) на
  правильной стороне границы. Ядро не меняется → нулевой риск регрессии
  расписания. Тестируется изолированно.
- **Вариант B-full — «Session Engine» с реестром режимов/стратегий.**
  Архитектурно чисто под будущее, но это «архитектура на 5 лет вперёд»,
  запрещённая приоритетом конституции (работающий продукт > простота); режимы
  Voice/Reading/Exam — Phase 2–3, не сегодня.

Разграничение, важное для конституции: «AI решает, когда показать карточку»
отклоняется. Решение «какую карту показать» — это **подача**, и мы оставляем её
в **детерминированном** слое, а не в AI. Отдельный `StudySession` делает эту
границу явной: ядро решает *что due*, сессия — *в каком порядке подать*.

## Decision

Выбран **Вариант B-minimal**. Создан `StudySession`
(`packages/engine/src/study-session.ts`) — отдельный от `LearningEngine`
детерминированный слой потока сессии. Метод `nextCard()`: сначала due-карты
(`due <= now`, порядок по `due`, tie-break по `id`), иначе learning/relearning
в окне `learnAheadMinutes` (по умолчанию 20). Использует **только** публичный
`engine.listCards()`; публичный API ядра расширять не потребовалось; ядро не
менялось.

## Consequences

**Плюсы:**
- SRP соблюдён: у ядра одна причина меняться (память), у сессии другая (поток).
- Ядро не тронуто → регрессия расписания невозможна; граница проверяема.
- `StudySession` и будущий AI Layer — **параллельные независимые потребители**
  публичного API ядра, а не звенья цепи (согласовано с `PROJECT_CONSTITUTION.md`,
  CORE ARCHITECTURE).
- Детерминизм и изолированная тестируемость (`study-session.test.ts`).

**Минусы / цена:**
- `nextCard()` вызывает `engine.listCards()` каждый раз — O(n) на выборку
  (для MVP-объёмов приемлемо; индексированный запрос горизонта — будущая
  оптимизация).
- Порядок сессии упрощён (по `due`, без interleaving new/learning-приоритета).
- Возможна лёгкая рассинхронизация счётчика статистики «dueNow» (строго
  `due <= now`) с тем, что показывает сессия через learn-ahead.

**Границы:** будущие режимы/лимиты/мультиколоды — как опции/стратегии
`StudySession` или новые независимые потребители ядра, а не ветки внутри
`LearningEngine`.
