# ADR-002 — Review Log as Source of Truth

**Статус:** Accepted · Phase 1

## Context

Ядро памяти хранит для каждой карты scheduling-состояние (`stability`,
`difficulty`, `reps`, `lapses`, `due`, `state` …). Нужно решить, что считать
**источником истины** о памяти пользователя. Требования конституции:

- нельзя случайно «сломать» уже посчитанную историю повторений;
- пользователь владеет своими данными (экспорт/бэкап в будущем);
- возможность будущей оптимизации/смены параметров алгоритма без потери
  истории; совместимость с экспортом в Anki-подобные форматы.

## Options

1. **Только изменяемое состояние на карте (без журнала).** Минимум данных, но
   история безвозвратно теряется при каждом ответе; невозможны аудит, честная
   статистика за период и будущий re-fit параметров; при баге планировщика
   восстановить память нельзя.
2. **Append-only Review Log как source of truth; scheduling на карте — кэш.**
   Каждый ответ добавляет иммутабельную запись. Больше данных, но история
   полна и восстановима.
3. **Журнал + событийный replay как единственный способ получить состояние
   (полный event sourcing).** Максимальная строгость, но избыточная сложность
   для Phase 1 (нужен готовый replay на каждый показ карты).

## Decision

Выбран вариант 2. `Review` (`packages/engine/src/types.ts`) — иммутабельная
append-only запись (`rating`, `reviewedAt`, `stateBefore`, `stateAfter`,
`dueAfter`, `stability`, `difficulty`, `scheduledDays`). `SchedulingState` на
карте — производный **кэш** для быстрых запросов. `EngineStore.appendReview`
только добавляет; при `deleteCard` журнал намеренно сохраняется.

## Consequences

**Плюсы:**
- История повторений полна, иммутабельна, пригодна для статистики и будущего
  re-fit параметров/экспорта.
- Основа для оффлайн-владения данными.
- `CardState` фиксируется в каждой записи → последовательность состояний
  воспроизводима из журнала (INV-5).

**Минусы / цена:**
- Больше хранимых данных, чем при «только состояние».
- Денормализация: часть scheduler-полей продублирована в `Review` ради аудита.

**Открытый вопрос (сознательно не закрыт в Phase 1):**
Инвариант «scheduling-кэш восстановим проигрыванием журнала» пока **не**
реализован как операция. `Review` не хранит `reps/lapses/learningSteps/
lastReview`, поэтому lossless-восстановление возможно **пересчётом** через
детерминированный `Scheduler` (косвенно подтверждается тестом детерминизма), а
не чтением полей. Явной функции `rebuild(cardId)` и её теста нет. Направления:
(а) replay через recomputation; (б) хранить полное состояние в каждом Review.
См. `ARCHITECTURE.md` §10 и `PROGRESS.md`.
