# ADR-004 — Retrieval Responsibility

**Статус:** Accepted · Phase 2

> Основан на архитектурной записке «Engine Public API Audit — Context
> Selection» (research-only, без изменений кода). Повторное исследование кода
> для этого ADR не проводилось; факты ниже — из аудита.
>
> Этот ADR фиксирует **распределение ответственности за retrieval**, а не
> проектирует Retrieval API. Интерфейсы, сигнатуры и реализация здесь
> сознательно не описываются — это предмет отдельной реализационной задачи,
> формулируемой **после** утверждения данного решения.

## Context

AI Layer (`packages/ai`, TASK_010) — первый read-only потребитель ядра. Сейчас
`ContextAssembler` берёт **полную** коллекцию через публичный API
(`listCardViews` + `getStats`) и передаёт её в prompt без отбора. Для маленьких
коллекций этого достаточно; для больших встаёт вопрос **Context Selection** —
получить релевантное **подмножество** данных, а не всё сразу.

Аудит публичного API Engine установил факты, определяющие рамку решения:

- **Публичного Search API не существует.** В `packages/engine` нет модуля/метода
  поиска, полнотекста, фильтра по контенту, тегам или релевантности.
- **Доступны ровно три формы отбора:** «всё» (`listCardViews`/`listCards`), «по
  временно́му окну `due`» (`getDueCards`/`getCardsDueBy`), «по уже известному id»
  (`getCard`/`getCardView`/`getNote`). Плюс агрегаты (`getStats`).
- **Отбор у́же полного набора по контенту / `deckId` / `state` в API отсутствует
  как механизм** — сегодня достижим только клиентской фильтрацией в памяти уже
  **после** полной выгрузки.
- **Порядок `listCards`/`listCardViews` не гарантирован** и различается между
  адаптерами Storage (`MemoryStore` — порядок вставки; `DexieStore` — порядок
  IndexedDB по ключу). Tie-break равных `due` в due-запросах также не
  специфицирован. Это подрывает детерминизм будущих retrieval-тестов.
- **Архитектурный принцип «Engine — единственный владелец данных» (TASK_010):**
  AI Layer — чистый read-only consumer, которому **запрещено** создавать
  собственный Storage, Search Engine, embeddings, индексы или кэш; все знания он
  получает исключительно из Engine.
- **Границы конституции:** доступ к данным только через публичный API (никогда в
  Storage напрямую); «минимальный публичный API ядра» (принцип №8) — расширение
  контракта ядра является отдельным, более серьёзным разговором; лог повторений
  — source of truth (ADR-002); граница «Engine ↔ потребители» закладывается
  заранее, т.к. дорого добавлять задним числом.

## Problem

Аудит довёл анализ до развилки и остановился: **чья это ответственность —
отобрать релевантное подмножество данных для потребителя (AI Layer и будущих),
когда «взять всё» перестаёт годиться?**

Вопрос именно об **ответственности и её месте**, а не о форме метода. Ответ
определяет, где вообще может жить любая будущая логика retrieval — и, как
следствие, остаётся ли принцип «Engine — единственный владелец данных»
несущим или размывается первым же практическим требованием.

## Options

**Вариант A — retrieval внутри AI Layer (потребителя).** Потребитель берёт
полный набор и сам фильтрует/ранжирует; в пределе — заводит собственный
индекс/поиск/кэш.
- *Плюсы:* ядро не меняется; быстро сегодня.
- *Минусы:* прямо нарушает жёсткое ограничение TASK_010 и принцип «Engine —
  единственный владелец данных» (потребитель обзаводится собственным
  представлением базы знаний); полная выгрузка не масштабируется; опора на
  недокументированный порядок → недетерминированные тесты; политика доступа к
  данным **размазывается** по потребителям — каждый следующий (UI, будущий AI)
  переизобретает отбор по-своему. Смешивает ось «данные» с осью «AI».

**Вариант B — retrieval как ответственность Engine (владельца данных),
предоставляемая через его публичный API.** Когда нужен отбор у́же полного
набора, эту возможность даёт **ядро** — как владелец данных, — а не потребитель.
- *Плюсы:* согласовано с принципом владения данными, ADR-002 и границей
  «доступ только через публичный API»; единая точка политики отбора,
  переиспользуемая всеми потребителями; гарантии (полнота, порядок, детерминизм),
  которых сегодня нет у list-методов, определяются **у владельца**, где им и
  место; AI Layer остаётся stateless read-only без собственного индекса.
- *Минусы:* требует осознанного, покрытого тестом **изменения контракта ядра**
  (принцип №8) — не бесплатно и не «по умолчанию»; обязывает явно задать
  гарантии порядка/детерминизма (аудит показал их отсутствие у list-методов);
  объём работы больше, чем у A. Конкретная форма — предмет отдельной задачи, не
  этого ADR.

**Вариант C — отдельный stateful retrieval/query-слой между Engine и
потребителями** (свой пакет с производными индексами/кэшем поверх публичного API
ядра).
- *Плюсы:* держит ядро минимальным; выносит отбор из AI Layer.
- *Минусы:* такой слой **владеет производным представлением базы знаний**
  (индекс/кэш) — ровно то, что принцип «Engine — единственный владелец данных»
  запрещает; появляется второй источник, требующий синхронизации с логом —
  source of truth (ADR-002). Если же сделать слой **без** собственного состояния
  (чистая композиция вызовов API), он вырождается либо в A (хелпер потребителя),
  либо в B (возможность владельца) — самостоятельной ценности не несёт, а сложность
  добавляет. Отклоняется.

## Decision

Выбран **Вариант B**. **Retrieval (Context Selection за пределами тривиального
«взять всё») — ответственность Engine как единственного владельца данных, и
предоставляется исключительно через его публичный API.** AI Layer и любой иной
потребитель **никогда** не владеют retrieval и не дублируют его: ни собственного
Storage, ни Search Engine, ни embeddings, ни индексов, ни кэша, ни прямого
доступа в Storage.

Это решение об **ответственности и границе**, а не о механизме:

- Оно **подтверждает** принцип «Engine — единственный владелец данных» (TASK_010)
  как несущий: первое практическое требование к отбору данных разрешается в
  пользу владельца, а не размывает принцип.
- Оно **ничего не меняет в коде и не расширяет публичный API сейчас.** Пока
  «взять всё» через существующий API достаточно для нужды потребителя —
  расширение не требуется (простота прежде архитектурной чистоты). Когда нужда
  превысит текущий API, соответствующая возможность добавляется **на стороне
  Engine**, а не обходится в потребителе.
- **Конкретная форма возможного расширения публичного API — вне рамок этого
  ADR** и не проектируется здесь: ни интерфейсов, ни сигнатур, ни семантики
  фильтрации/порядка. Любое такое расширение — изменение контракта ядра
  (принцип №8) и потому оформляется отдельной реализационной задачей с явным
  обоснованием необходимости и тестом на регрессию памяти/поведения (INV-2),
  либо не делается вовсе, если нужды нет.

Что решение **не** делает (сознательно): не проектирует Retrieval API; не меняет
Engine, его публичный API или Storage; не присваивает принципу владения данными
номер инварианта (INV-10 остаётся не присвоенным до отдельной задачи).

## Consequences

**Плюсы:**
- Граница «данные принадлежат Engine» остаётся явной и несущей; ось «память/
  данные» не смешивается с осью «AI/подача» (согласовано с ADR-003 и CORE
  ARCHITECTURE конституции).
- Политика отбора будет иметь **единственное** место (владелец), переиспользуемое
  всеми потребителями; детерминизм и порядок — определяемые и тестируемые там,
  где хранятся данные.
- AI Layer гарантированно остаётся stateless read-only; guard-тесты TASK_010
  (нет доступа в Storage, нет своего индекса) остаются валидны и не
  подрываются будущим retrieval.
- Если в будущем возникнет необходимость в более развитых возможностях
  Retrieval, они должны развиваться как часть публичного API Engine, а не AI
  Layer.

**Минусы / цена:**
- Любой реальный отбор у́же «всего» потребует **осознанного изменения контракта
  ядра** — по принципу №8 это отдельный разговор и отдельная задача, не быстрый
  путь. Это принятая цена сохранения границы владения данными.
- Пока такого расширения нет, AI Layer вынужден работать в рамках «взять всё /
  due-окно / по id»; на очень больших коллекциях полная выгрузка — известное
  ограничение, снимаемое только будущим расширением API на стороне Engine.
- Отсутствующие сегодня гарантии порядка/детерминизма list-методов придётся явно
  определить при вводе любой retrieval-возможности — иначе retrieval-тесты будут
  опираться на деталь реализации Storage.

**Границы:** менять реализацию за портами (`Scheduler`, `EngineStore`) — можно;
**расширять публичный контракт `LearningEngine` ради retrieval — только через
отдельную задачу** с обоснованием и тестом. Смена самого решения об
ответственности — новый ADR, замещающий этот, а не правка данного (ADR
иммутабелен по смыслу).
