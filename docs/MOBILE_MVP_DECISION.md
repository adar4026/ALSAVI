# Mobile MVP Decision — PWA as the first iPhone client

**Статус:** Accepted · основание для TASK_015
**Дата:** 2026-07-06

Этот документ фиксирует решение о способе доставки ALSAVI на iPhone. Он —
результат серии research-only итераций (сравнение PWA / Capacitor / React
Native; топология AI Layer / OllamaProvider; storage-persistence и ITP
verification; уточнение Q1 по WebKit «App-Bound Domains»; выравнивание стандарта
доказательности). Решение принято основателем (Alex). Здесь оно только
записывается — не переобосновывается.

## Решение

**Первый мобильный клиент ALSAVI — PWA поверх существующего `apps/web`**
(Safari → «Добавить на экран Домой»), без нового UI-клиента и без нативной
оболочки.

## Почему PWA (кратко)

Определяющие критерии — **стоимость установки/дистрибуции, объём изменений и
архитектурный риск**, а не storage:

- **Наименьший объём и архитектурный риск:** переиспользует `apps/web` целиком;
  Engine и публичный API Engine **не затрагиваются** (порт `EngineStore` /
  `DexieStore` остаётся); это платформенная адаптация, а не архитектурное
  изменение.
- **Наименьшая стоимость установки:** без Apple Developer-аккаунта, Xcode,
  CocoaPods и подписи — установка через Safari «на экран Домой».

## Storage — сознательно НЕ является аргументом выбора

После storage/ITP-исследования и уточнения Q1 стандарт доказательности
выровнен между вариантами (строго Confirmed / Supported / Community):

- **Confirmed:** WKWebView **не исключён** из ITP по умолчанию (iOS 14.0, WebKit
  «App-Bound Domains»). Home-screen web apps имеют **отдельный от Safari
  счётчик** использования (WebKit blog 10218).
- **Supported (не Confirmed):** что конкретный 7-дневный storage-cap применяется
  к WKWebView **так же, как в Safari** (композиционный вывод; параметры eviction
  для WKWebView официально не специфицированы).
- **Community (максимум):** «Apple не ожидает удаления данных home-screen apps»
  (комментарий J. Wilander через сторонние источники).
- **Maintainer:** Capacitor документирует storage-pressure reclaim и «transient»
  IndexedDB на iOS.

**Вывод:** ни PWA, ни Capacitor не имеют документально подтверждённого
преимущества друг перед другом по механизму inactivity-eviction — неопределённость
симметрична (с разными основаниями). Поэтому storage **исключён** как аргумент
в паре PWA ↔ Capacitor; реальным storage-дифференциатором остаётся только React
Native (native SQLite / App Sandbox — вне WebKit storage subsystem). Durability
локального хранения закрывается **отдельным эмпирическим тестом** (2-недельный
on-device inactivity-тест), вне scope первого установочного билда.

## Границы решения

- **AI Layer — вне мобильного MVP.** `@alsavi/ai` сегодня не подключён к
  `apps/web`; on-device Ollama невозможен во всех вариантах (нет Ollama на
  устройстве; `127.0.0.1` = телефон; mixed-content/ATS). Любой реальный AI на
  устройстве потребует удалённого HTTPS-провайдера за существующей абстракцией
  `LLMProvider` — это deployment-концерн, не изменение Engine, и отдельная
  будущая задача.
- **Engine / публичный API Engine / `EngineStore` — не затрагиваются.**
- **Локальная разработка/тест на устройстве** — через локальный HTTPS (mkcert),
  без туннелей и staging.

## Когда пересмотреть (условия для других вариантов)

- **Capacitor** — если потребуются **нативные возможности** или **App-Store**-
  дистрибуция (не ради storage — это преимущество опровергнуто). Вероятно
  потребует отдельного ADR.
- **React Native** — если **durability локальных данных** и нативность объявлены
  обязательными: единственный вариант вне WebKit storage policy, но наибольший
  объём (UI заново + новый адаптер `EngineStore`) и отдельный ADR.

## Реализация

Первый установочный билд — **TASK_015** (`tasks/TASK_015.md`), который ссылается
на данный Decision. Follow-up — отдельный 2-недельный on-device inactivity-тест
durability, не блокирующий сам факт установки.
