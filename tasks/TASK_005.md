# TASK_005 — Review Log Replay (CardState Reconstruction)

Перед началом работы сохрани этот файл как `tasks/TASK_005.md` дословно.

Прочитай: CLAUDE.md, PROJECT_CONSTITUTION.md, ARCHITECTURE.md, ENGINE.md, PROGRESS.md — включая инвариант 9 ("CardState всегда должен быть воспроизводим из Review Log") и открытый вопрос про replay, зафиксированный в ARCHITECTURE.md/PROGRESS.md.

------------------------------------------------------------

## КОНТЕКСТ

Конституция и ARCHITECTURE.md утверждают: Review Log — source of truth, CardState — производный кэш, воспроизводимый из лога. Сейчас это утверждение подкреплено только тестами детерминизма (одинаковая история → одинаковое расписание при пересчёте вперёд), но нет самой операции "взять Review Log карточки → пересчитать CardState с нуля, игнорируя сохранённый кэш". Это открытый технический вопрос, который стоит закрыть до релиза, иначе инвариант — декларация, а не проверяемый факт.

------------------------------------------------------------

## ЦЕЛЬ

Реализовать функцию восстановления (rebuild/replay), которая берёт полный Review Log карточки и заново вычисляет CardState через Scheduler, не читая сохранённое состояние. Добавить тест эквивалентности: пересчитанный из лога CardState должен совпадать с тем, что хранится как кэш, для любой существующей карточки.

------------------------------------------------------------

## ЭТАП 1 — АНАЛИЗ

Не изменяй код. Определи:

1. Каких полей сейчас не хватает в ReviewLogEntry, чтобы полностью восстановить CardState только из лога (в TASK_001 отмечалось, что Review хранит stability/difficulty/scheduledDays, но не reps/lapses/learningSteps/lastReview — проверь, актуально ли это сейчас после TASK_003).
2. Если полей не хватает — можно ли их добавить без breaking change для уже существующих записей лога (например, как опциональные, восстанавливаемые по умолчанию для старых записей), или нужна миграция.
3. Где логично разместить саму операцию replay — на LearningEngine (публичный метод) или как отдельная утилита поверх Scheduler + EngineStore.

Покажи анализ. Жди подтверждения, прежде чем писать код.

------------------------------------------------------------

## ЭТАП 2 — РЕАЛИЗАЦИЯ

- Реализуй метод (например, `LearningEngine.rebuildCardState(cardId)`), который читает весь Review Log карточки и пересчитывает CardState через Scheduler, не используя сохранённый кэш как вход.
- Не меняй поведение существующих методов (`review()`, `getDueCards()`, превью интервалов) — это отдельная, дополнительная операция, не замена текущего пути.
- Если нужно расширить ReviewLogEntry — сделай это как обратно совместимое расширение, с планом для уже существующих записей лога (какое значение подставляется для карточек, созданных до этой задачи).

------------------------------------------------------------

## ЭТАП 3 — ТЕСТЫ

- Тест эквивалентности: для набора карточек с разной историей (несколько Again подряд, переход Learning→Review, разные рейтинги) — `rebuildCardState()` должен дать тот же результат, что и сохранённый кэш.
- Тест на случай неполного/старого лога (если применимо после решений Этапа 1).
- Старые тесты не должны сломаться.

------------------------------------------------------------

## ЭТАП 4 — ПРОВЕРКА

- Review Log остаётся append-only (replay не мутирует историю, только пересчитывает состояние);
- граница Engine/AI не затронута.
