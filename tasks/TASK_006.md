------------------------------------------------------------

## КОНТЕКСТ

Два связанных технических долга, оба про эффективность чтения из EngineStore — стоит закрывать вместе, так как решения (индексы, стратегия загрузки) вероятно пересекаются:

1. **Due-horizon (с TASK_001/TASK_002).** `StudySession.nextCard()` и `dueCount()` вызывают `listCards()` — полный обход всех карточек, O(n) на каждый вызов.
2. **N+1 в CardView (с TASK_003).** После введения Note, `listCardViews()` для каждой карты делает отдельный лукап заметки (`getNote(card.noteId)`) — то есть N+1 чтений на список из N карт.

Для MVP-объёмов оба не критичны, но начнут заметно тормозить при росте коллекции карточек (сотни-тысячи карточек на пользователя).

## ЦЕЛЬ

Заменить оба паттерна полного/N+1 обхода на индексированные и батч-запросы, не меняя наблюдаемое поведение `nextCard()`, `dueCount()` и `listCardViews()` — только их производительность.

## ЭТАП 1 — АНАЛИЗ

Не изменяй код. Определи:

**Про due-horizon:**
1. Как `EngineStore`/`DexieStore` хранят карточки сейчас — есть ли уже индекс по полю due (проверь, не изменилась ли схема после миграции v2 в TASK_003), или потребуется его добавить.
2. Какой именно запрос нужен: "все карточки с due <= threshold", где threshold — динамическая граница (now или now + learnAheadMinutes) — можно ли выразить как индексированный range-запрос в Dexie.
3. Меняется ли контракт `EngineStore` (нужен ли новый метод вроде `listCardsDueBefore(threshold)`), или существующий `listCards()` можно оставить как есть для прочих сценариев (например, экран «Карточки», где нужен полный список), добавив более узкий метод только для StudySession.

**Про N+1 в CardView:**
4. Сколько заметок обычно соответствует списку карт (после TASK_003 у каждой карты ровно одна заметка через `noteId`, но одна заметка может иметь несколько карт-сестёр — оцени, насколько велика избыточность чтения одной и той же Note несколько раз).
5. Можно ли решить это батч-загрузкой заметок (например, `getNotesByIds(ids)` с дедупликацией) без превращения `EngineStore` в more широкий join-слой — граница ответственности EngineStore (простое хранилище) не должна расшириться до query-построителя.

**Общее:**
6. Требуется ли миграция схемы Dexie для добавления индекса, и что произойдёт с уже существующими локальными данными пользователей (после TASK_003 в базе уже есть реальные Note и мигрированные карты — риск повторной миграции стоит оценить конкретно).

## ЭТАП 3 — ТЕСТЫ

- Тест эквивалентности для due-horizon: результат нового индексированного запроса должен совпадать с тем, что раньше давал `listCards()` + фильтрация в StudySession, для одних и тех же входных данных.
