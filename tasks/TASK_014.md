## Предыстория (для контекста, не для повторного обоснования)
Три research-only итерации (без изменений репозитория) установили эмпирически:

1. `MemoryStore.listCards`/`listCardViews` и `DexieStore.listCards`/`listCardViews`
   систематически возвращают разный порядок на идентичных данных (20/20 живых прогонов).
   Причина — публичный контракт `EngineStore.listCards` и `LearningEngine.listCardViews`
   вообще не специфицирует порядок. Ни один адаптер не нарушает контракт — нарушать нечего.
2. Гипотеза о влиянии через Context Budget Guard опровергнута. Guard ничего не усекает,
   только выбрасывает исключение. Реальный механизм другой: разный порядок карточек →
   разный prompt → разный ответ content-sensitive модели.
3. Web → export → CLI уже сегодня случайно согласованы, потому что оба используют
   DexieStore. Это не production-баг. Это недоспецифицированный контракт и слепая зона
   тестовой инфраструктуры.
4. Review Log не может быть источником порядка. Он не содержит новых карточек, а replay
   реконструирует состояние одной карты, а не порядок множества.
5. Среди всех исследованных вариантов (`card.id`, `noteId`, `createdAt`, `due`, порядок
   Review Log) минимальным решением признан **card.id**.
6. Проверено, что ни один существующий потребитель (AI Layer, CLI, Web UI) не зависит
   семантически от порядка создания карточек.

Полные протоколы исследований находятся в истории предыдущих research-only итераций и
повторно не воспроизводятся.

## Цель
Устранить недоспецифицированность публичного контракта Engine в части порядка
перечисления (`listCards()`, `listCardViews()`), которая приводит к адаптеро-зависимому
поведению и не обнаруживается существующими тестами.

Это **не исправление production-багов**. Это фиксация публичного контракта Engine и
устранение слепой зоны тестирования.

---

## Что входит в задачу

### 1. Спецификация контракта
В `ARCHITECTURE.md` и `ENGINE.md` явно зафиксировать:

**Гарантия.** Все реализации `EngineStore` обязаны возвращать результат в одном и том же
полном, детерминированном, стабильном, тотальном порядке при идентичных данных.

**Нормативная спецификация.** В текущей версии контракта этот порядок определяется
`card.id` в лексикографическом порядке. Все реализации `EngineStore` обязаны соблюдать
данный порядок.

**Изменение нормативного порядка.** Допускается только через отдельный ADR, отдельную
TASK и явное изменение публичного контракта Engine. Изменение нормативного порядка
считается breaking architectural change.

**Scope.** Изменение касается исключительно `listCards()` и `listCardViews()`. Не
изменяются `listDueCards()`, Selection, Retrieval, фильтрация, лимиты, окна, Search,
любые новые query-возможности.

### 2. Реализация

**MemoryStore.** Заменить эмерджентный порядок `Map` на явную сортировку по `card.id`,
не изменяя внутреннее хранение. Сортировка выполняется только при возврате результата.

**DexieStore.** Явно задавать порядок по `card.id` в запросе. Не полагаться на побочный
эффект `toArray()`.

**LearningEngine.** Убедиться, что `listCardViews()` наследует порядок от `listCards()`
без дополнительной сортировки.

### 3. Тестовая инфраструктура
Добавить `fake-indexeddb` в `devDependencies` исключительно для тестовой инфраструктуры.
Производственный код не должен зависеть от `fake-indexeddb`.

Добавить кросс-адаптерный regression test, который проверяет, что `MemoryStore` и
`DexieStore` возвращают идентичный порядок для одной и той же коллекции. Тест должен быть
полностью детерминирован — фиксированный seed или фиксированный набор id, гарантирующий,
что порядок вставки не совпадает с порядком id.
