# TASK_010 — AI Layer (Phase 2): First Read-Only Consumer

## Цель

Построить первый AI Layer поверх существующего Engine, не изменяя ядро
и не расширяя его публичный API.

AI Layer — независимый потребитель Engine, а не третий последовательный
слой в стеке. Он полностью зависит от Engine, но Engine ничего не знает
о существовании AI Layer.

После выполнения задачи должна работать программная точка входа
`AIService.answer(question)`, возвращающая ответ на основе данных ALSAVI.
UI или CLI для сквозного пользовательского сценария — вне рамок этой
задачи.

## Обязательно перечитать

CLAUDE.md, PROJECT_CONSTITUTION.md, ARCHITECTURE.md, ENGINE.md,
PROGRESS.md, ADR-001, ADR-002, ADR-003.

## Жёсткие ограничения

- Не менять Engine, его публичный API, Storage, Scheduler, FSRS, Search,
  Backup, Import, Export и существующие инварианты.
- AI Layer обращается к данным **исключительно через существующий
  публичный API Engine**. Прямой доступ к DexieStore или внутренним
  модулям Storage из пакета `ai` запрещён — так же строго, как Engine
  не имеет доступа к сети и AI.
- AI Layer использует существующие возможности Engine по получению
  данных. **Если существующего публичного API недостаточно для
  эффективного получения необходимого контекста, исполнитель обязан
  остановиться и зафиксировать архитектурный вопрос основателю — не
  реализуя собственный индексатор, поисковый движок или дублирующую
  систему поиска внутри AI Layer.**
- Запрещается создавать внутри AI Layer:
  - собственный Search Engine;
  - собственный Storage;
  - собственные Embeddings;
  - собственные индексы.
  Все знания AI Layer получает исключительно из Engine.

## Архитектурный принцип

Engine является единственным владельцем данных. AI Layer — чистый
read-only consumer и не создаёт собственного представления базы знаний.

Это **принцип, а не нумерованный инвариант.** По правилу проекта
инвариант заслуживается: если этот принцип подтвердится последующими
независимыми изменениями, он может быть оформлен как INV-10 отдельной
задачей. В рамках TASK_010 номер INV-10 не присваивается.

## Структура пакета

```
packages/
  ai/
    AIService.ts
    PromptBuilder.ts
    ContextAssembler.ts
    AnswerGenerator.ts
    providers/
      MockProvider.ts
```

### AIService

Точка входа: `answer(question: string): Promise<AIAnswer>`.
Выполняет **только оркестрацию** вызовов других компонентов
(ContextAssembler → PromptBuilder → AnswerGenerator через Provider →
ответ). Не содержит собственной логики поиска, формирования prompt
или генерации ответа.

Контракт ответа:

```ts
interface AIAnswer {
  readonly answer: string;
  readonly sources?: readonly string[];
}
```

Поле `sources` определено в контракте, но в TASK_010 не заполняется
(остаётся `undefined`). Оно зарезервировано под будущие citations /
source references и в этой задаче не реализуется. Контракт возвращается
объектом (а не голой строкой), чтобы последующие задачи могли добавлять
поля без ломающего изменения API AI Layer.

### ContextAssembler

Единственная ответственность — собрать контекст из данных Engine и
подготовить его для PromptBuilder. Не выполняет семантического
ранжирования, не модифицирует документы, не сокращает их с помощью LLM
и не принимает решений о содержании ответа. Не знает про LLM, UI и
PromptBuilder. Обращается к Engine только через его текущий публичный API.

### PromptBuilder

Формирует текст prompt из готового контекста. Не выполняет поиск, не
вызывает модель, не содержит доменной бизнес-логики.

### AnswerGenerator / LLMProvider

Абстракция над LLM за интерфейсом:

```ts
interface LLMProvider {
  generate(prompt: string): Promise<string>;
}
```

`AnswerGenerator` — сервис, использующий `LLMProvider` для генерации
ответа. Он не знает о конкретной реализации провайдера и зависит только
от интерфейса `LLMProvider`.

В рамках задачи реализуется только `MockProvider` — детерминированный
провайдер без сетевых вызовов, возвращающий заранее определённый
результат по входному prompt для обеспечения полностью воспроизводимых
unit-тестов. Реальная интеграция (OpenAI / Ollama / Claude) — вне рамок
TASK_010.

## Definition of Done

1. Пакет `packages/ai` создан со всеми перечисленными модулями.
2. Guard-тест: ни один файл Engine не импортирует что-либо из `ai`
   (симметрично существующему guard-тесту на network/AI-импорты в Engine).
3. Guard-тест: ни один файл `packages/ai` не импортирует DexieStore или
   внутренние модули Storage напрямую — доступ к данным только через
   публичный API Engine.
4. Unit-тесты на каждый модуль отдельно:
   - ContextAssembler: на фиксированном наборе данных Engine
     детерминированно возвращает ожидаемый контекст (без реального
     Provider).
   - PromptBuilder: на фиксированном контексте возвращает ожидаемый prompt.
   - AIService: интеграционный unit-тест на MockProvider — по заданному
     question возвращает ожидаемый AIAnswer end-to-end внутри пакета `ai`
     (поле `sources` при этом `undefined`).
5. LLM полностью скрыта за интерфейсом `LLMProvider`; ни один модуль,
   кроме конкретного провайдера, не знает деталей реализации модели.
6. Публичный API Engine не изменён. Это подтверждается как отсутствием
   diff в файлах экспорта Engine, так и правилом: если возникла
   необходимость расширить API — реализация прекращается и вопрос
   выносится основателю.
7. Все существующие тесты (engine, anki-import, backup) продолжают
   проходить без изменений.
8. Обновлены ARCHITECTURE.md, ENGINE.md и PROGRESS.md:
   - ARCHITECTURE.md — новый раздел: AI Layer как независимый consumer
     Engine; зафиксирован архитектурный принцип «Engine — единственный
     владелец данных» (без присвоения номера инварианта).
   - ENGINE.md — явно зафиксирована граница ответственности Engine
     относительно AI Layer.
   - PROGRESS.md — статус TASK_010.
9. AI Layer остаётся полностью stateless: не хранит собственную БД, не
   кэширует документы, не создаёт собственных индексов, не сохраняет
   состояние между вызовами.

## Явно вне рамок TASK_010

- Реальные LLM-провайдеры (OpenAI / Ollama / Claude).
- Streaming, citations, source references, multi-turn conversation
  (поле `sources` в `AIAnswer` зарезервировано, но не заполняется).
- UI или CLI для сквозного сценария «пользователь → AI Layer».
- Любые изменения в Engine, включая расширение публичного API.
- Присвоение номера INV-10 архитектурному принципу владения данными.

## Открытый вопрос при реализации

Если выяснится, что текущий публичный API Engine не позволяет получить
необходимый контекст для ContextAssembler — остановиться и зафиксировать
это как архитектурный вопрос к основателю. Не решать самостоятельно и не
строить обходных механизмов (индексов, поиска, кэшей) внутри AI Layer.
