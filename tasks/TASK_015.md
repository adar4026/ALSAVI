Approved for implementation.

## Решение, на котором строится задача (для контекста, не для пересмотра)

- PWA поверх существующего `apps/web`, без нового UI-клиента.
- Engine и публичный API Engine не затрагиваются.
- Storage-риск (inactivity-eviction) не является аргументом выбора — он
  симметрично неопределён между PWA и Capacitor (см. research); закрывается
  отдельным эмпирическим тестом, не входит в scope этой задачи.
- AI Layer сознательно вне scope — не интегрирован в `apps/web`.
- Локальная разработка/тестирование на устройстве — через локальный HTTPS
  (mkcert), не через туннель или staging.

## Цель

Сделать существующий `apps/web` устанавливаемым на iPhone через
Safari → «Добавить на экран Домой», без изменения архитектуры приложения,
Engine или AI Layer. Результат — приложение, которое можно установить на
реальное устройство и начать тестировать функциональность
Engine/StudySession (карточки, review-сессии, интервалы FSRS).

Это **не** полировка UI, **не** новая функциональность, **не** интеграция
AI на мобильном.

## Что входит в задачу

### 1. PWA-манифест и иконки
- `manifest.webmanifest`: name, short_name, `display: standalone`,
  theme_color, background_color, набор иконок (минимум 192×192, 512×512).
- `apple-touch-icon` и связанные Apple-специфичные `<meta>`-теги в
  `index.html` (`apple-mobile-web-app-capable`,
  `apple-mobile-web-app-status-bar-style`, и т.п.).
- Подключение манифеста и мета-тегов в `index.html`.

### 2. Service Worker
- Минимальный service worker: кэширование статического app-shell для
  офлайн-старта после первого запуска.
- **Service Worker не должен менять существующую архитектуру загрузки
  приложения.** Разрешается только app-shell caching (статические ассеты:
  JS/CSS/HTML-шелл, иконки). **Запрещается** runtime caching пользовательских
  данных, IndexedDB, API-запросов или любой бизнес-логики — это осталось бы
  вне контроля Engine/DexieStore и создало бы второй, недокументированный
  источник состояния.
- Без background sync, без push — это явно вне scope (см. Non-Goals).

### 3. Локальный HTTPS для разработки (mkcert)
- Настройка mkcert для локальной разработки: генерация сертификата для
  локального IP/hostname Mac в общей Wi-Fi сети.
- Конфигурация dev-сервера (Vite) для запуска по HTTPS с этим сертификатом.
- Задокументировать шаги в `apps/web/README.md` (или аналогичном месте):
  как поднять локальный HTTPS-сервер и получить доступ с iPhone в той же
  сети.

### 4. Установка и проверка на устройстве

Эта часть содержит **интерактивные шаги, не выполнимые автономно агентом**
— они требуют физического доступа к Mac и iPhone и подтверждаются
пользователем, а не агентом:
- установка root-сертификата mkcert на iPhone (профиль через
  AirDrop/почту);
- **явное включение доверия сертификату**: Settings → General → About →
  Certificate Trust Settings (это отдельный ручной шаг, не происходит
  автоматически при установке профиля);
- открытие приложения в Safari на iPhone по локальному HTTPS;
- Safari → Поделиться → «Добавить на экран Домой»;
- проверка запуска в standalone-режиме (без адресной строки Safari);
- базовая проверка функциональности: создание/просмотр карточек, review-
  сессия, применение FSRS-интервалов.

Роль агента здесь — подготовить точную, воспроизводимую инструкцию для
каждого из этих шагов (см. DoD 5–6), не выполнять и не подтверждать их
самостоятельно.

## Явно вне рамок (Non-Goals)

- Push-уведомления.
- Background sync.
- Интеграция AI Layer в `apps/web` (AI остаётся вне мобильного MVP).
- App Store / нативная дистрибуция.
- Capacitor, React Native, любая нативная оболочка.
- Туннели (ngrok/cloudflared), staging-сервер, публичный деплой.
- Любые изменения Engine, публичного API Engine, EngineStore.
- 2-недельный inactivity-тест на реальном устройстве — это отдельная,
  последующая задача (или отдельный этап этой же задачи после установки,
  см. Риски), не блокирующая сам факт установки и базовой проверки.
- Любая доработка UI сверх необходимого для PWA-соответствия (иконки,
  манифест) — не полировка дизайна.

   display: standalone, иконки минимум двух размеров.
2. `apple-touch-icon` и Apple meta-теги добавлены в `index.html`.
3. Минимальный service worker зарегистрирован, кэширует app-shell.
4. Локальный HTTPS через mkcert настроен и задокументирован
   (воспроизводимая инструкция в README).
**Автономная часть (выполняет и подтверждает агент):**

5. Подготовлена воспроизводимая инструкция по установке root-сертификата
   mkcert и включению Certificate Trust на iPhone (пошаговая, для конкретной
   версии iOS, если это известно, или с оговоркой про возможные отличия
   между версиями).
6. Подготовлена воспроизводимая инструкция установки PWA через
   Safari → «Добавить на экран Домой».
7. Engine, публичный API Engine, AI Layer — не изменены.
8. `PROGRESS.md` обновлён с записью о TASK_015 и ссылкой на Mobile MVP
   Decision.
9. Изменения не выходят за рамки Non-Goals.

**Часть, требующая физического доступа к устройству (подтверждает
пользователь — вне рамок автономного выполнения агентом):**

10. Пользователь подтверждает: приложение открыто в Safari на iPhone по
    HTTPS без сертификатных предупреждений.
11. Пользователь подтверждает: приложение добавлено на экран «Домой» и
    запускается в standalone-режиме.
12. Пользователь подтверждает: базовая функциональность работает на
    устройстве — карточки, review-сессия, FSRS-интервалы идентичны
    десктопной версии.

Агент не должен утверждать выполнение пунктов 10–12 от своего имени —
эти пункты закрываются отдельным подтверждением после того, как агент
завершил автономную часть.

## Риски

- Установка root-сертификата и включение доверия на iPhone — процесс,
  зависящий от версии iOS; шаги могут отличаться между версиями. Не
  блокер, но требует внимательности при документировании инструкции.
- Service worker на iOS Safari имеет известные особенности кэширования
  (см. предыдущий mobile research) — минимальный SW снижает поверхность
  этого риска, но не устраняет полностью; не в scope этой задачи чинить
  все известные WebKit SW-баги, только обеспечить базовый офлайн-старт.
- Долговременная надёжность локального хранения (IndexedDB eviction) —
  осознанно не проверяется в этой задаче. Следующий шаг после TASK_015 —
  отдельный 2-недельный inactivity-тест на этой же установленной сборке.
