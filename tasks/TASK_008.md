## ВАЖНО — ХАРАКТЕР ЭТОЙ ЗАДАЧИ

Это первая задача, где внешний формат данных сложнее и менее предсказуем, чем всё, что было раньше. `.apkg` — это не простой формат, а маленькая экосистема с несколькими версиями схемы, произвольными типами заметок и исторической историей повторений в чужой модели алгоритма (SM-2), тогда как у ALSAVI — FSRS.

Поэтому эта задача имеет **обязательную фазу разведки формата ДО любого проектирования и кода**. Не проектируй импорт на основе предположений о формате — сначала разведай реальную структуру на настоящем файле, доложи факты, и только после подтверждения переходи к дизайну.

Не пытайся поддержать весь Anki за один раз. Цель — минимальный честный импорт, а не полная совместимость.

## ЭТАП 1 — ТРИ РАЗВИЛКИ (решить явно, до дизайна)

На основе разведки (Этап 0), а не предположений, дай рекомендацию по трём вопросам. Для каждого — вариант, обоснование, и что сознательно НЕ поддерживаем на этом этапе:

**Развилка 1 — версии формата.** Какие версии схемы `.apkg` поддерживаем сейчас (старый `collection.anki2` / новый `collection.anki21` / новейший)? Рекомендация — начать с одной наиболее распространённой версии, остальные — явный отказ с понятным сообщением пользователю, а не молчаливый сбой.

**Развилка 2 — маппинг типов заметок (главный дизайн-вопрос).** Anki-заметка имеет произвольный note type с N именованными полями и M шаблонами (→ M карточек). Модель ALSAVI сознательно сужена до Note `{front, back}` + Card `{template: forward|reverse}`. Как маппить:
- заметку с ровно 2 полями и 1-2 шаблонами → прямое соответствие вашей модели;
- заметку с 3+ полями, cloze, или сложными шаблонами → ?

Рекомендация: поддержать только заметки, которые чисто ложатся в модель `{front, back}` (двухполевые basic / basic-and-reversed), а всё остальное — **пропустить с явным отчётом пользователю** («N заметок пропущено: неподдерживаемый тип»), а не пытаться силой впихнуть в 2 поля с потерей данных. Обоснуй, согласен ли ты с этим сужением или видишь лучший минимальный вариант.

**Развилка 3 — судьба истории повторений (revlog).** Anki `revlog` — это история в модели SM-2. У ALSAVI Review Log — source of truth в модели FSRS (ADR-002). Варианты:
- (a) игнорировать revlog: импортированные карточки заводятся как **новые** (state=new, чистый FSRS с нуля);
- (b) пытаться перенести историю повторений в ваш Review Log.

Рекомендация — (a), потому что перенос SM-2-истории в FSRS-модель — это семантически лукавый маппинг чужого алгоритма, который может исказить расписание и нарушить инвариант «Review Log — детерминированный source of truth в нашей модели». Импортированная карточка как новая — честно и предсказуемо. Обоснуй с точки зрения ADR-002 и конституции, согласен ли ты.

Покажи рекомендации по всем трём. Жди подтверждения, прежде чем переходить к дизайну.

## ЭТАП 2 — ПРОЕКТИРОВАНИЕ (после подтверждения, без кода)

**Архитектурное разделение импорта на два независимых слоя (обязательно).** Импорт — это не один модуль, а две разные ответственности с разными осями изменения (та же логика, что в ADR-003):

- **Anki Parser** — отвечает только за чтение `.apkg` (zip → SQLite → anki-объекты) и преобразование его во внутреннее промежуточное представление. **Не знает о Note/Card ALSAVI.** Меняется, когда меняется формат Anki.
- **Anki Import Mapper** — преобразует это промежуточное представление в модель ALSAVI через публичный API LearningEngine (`addNote` и т.д.). **Не знает о ZIP или SQLite.** Меняется, когда меняется модель ALSAVI.

Промежуточное представление между ними — граница и естественная точка тестирования: Mapper можно тестировать на синтетических anki-объектах без реального zip-файла. Это прямо снимает зависимость части тестов от наличия `.apkg` в окружении.

Опиши:

- где живёт импорт — это отдельный модуль/слой, НЕ часть LearningEngine (парсинг чужого формата — не ответственность ядра памяти); импорт должен использовать существующий публичный API движка (`addNote` и т.д.), а не писать в хранилище напрямую;
- как парсится `.apkg` (какая библиотека для zip, как читается SQLite в браузере — sql.js или аналог; проверь, что это вписывается в оффлайн/локальную философию и не тянет сетевых зависимостей в рантайме);
- как заметки маппятся в вашу модель (по решению Развилки 2);
- как обрабатываются медиафайлы (скорее всего — на этом этапе НЕ поддерживаем, пропускаем с отчётом; обоснуй);
- как выглядит отчёт пользователю (сколько импортировано, сколько пропущено и почему).

**Инвариант границ данных (важно, по опыту TASK_007).** Импорт ДОБАВЛЯЕТ заметки к существующей коллекции, а не заменяет/пересоздаёт базу. Не делай `deleteDatabase` / очистку IndexedDB ради импорта — в TASK_007 обнаружено, что удаление/пересоздание Dexie при открытом соединении вызывает deadlock. Если по анализу окажется, что пересоздание БД всё же необходимо — остановись и обоснуй отдельно, не делай молча.

Если для импорта потребуется новый метод публичного API LearningEngine — остановись и обсуди (принцип «минимальный API ядра», Architecture Principle №8). Скорее всего существующего `addNote` достаточно.

## ЭТАП 3 — РЕАЛИЗАЦИЯ (после подтверждения дизайна)

- Два отдельных слоя: Anki Parser (zip/sqlite → промежуточное представление) и Anki Import Mapper (представление → модель ALSAVI через публичный API движка). Parser не импортирует ничего из модели ALSAVI; Mapper не импортирует ничего про zip/sqlite.
- Ни один из слоёв не в ядре; Mapper использует публичный API движка для создания заметок/карт.
- Неподдерживаемые заметки — пропускаются с подсчётом, не роняют весь импорт.
- Ошибка парсинга одного файла — понятное сообщение, не тихий сбой.

------------------------------------------------------------

## ЭТАП 4 — ТЕСТЫ

- **Mapper на синтетических anki-объектах (без реального .apkg):** промежуточное представление базовой двухполевой заметки → корректная Note + Card(s). Это основной тест маппинга, не зависящий от наличия файла.
- Basic-and-reversed → Note + forward + reverse.
- Неподдерживаемый тип заметки → пропущен, посчитан в отчёте, остальные импортированы.
- Импорт добавляет к существующим данным, не затирает их (создай карту вручную, потом импортируй — обе группы на месте).
- Импортированные карточки — state=new (по Развилке 3a), участвуют в StudySession как обычные.
- **Parser на реальном/минимальном `.apkg`** (если файл доступен): корректно извлекает промежуточное представление. Если файла нет — явно скажи это, покрой Parser отдельно при получении файла, но Mapper протестируй уже сейчас на синтетике.
- Старые тесты зелёные.

Не имитируй прохождение теста, которого нельзя выполнить без реального файла. Разделение Parser/Mapper специально сделано так, чтобы Mapper тестировался всегда, а Parser — когда файл доступен.
