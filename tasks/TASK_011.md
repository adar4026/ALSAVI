## Фаза 1 — Анализ (до написания кода)

Не приступай к написанию кода сразу. Сначала изучи существующую
реализацию AI Layer и ответь себе на вопросы:

- соответствует ли текущая структура `packages/ai` требованиям TASK_010;
- где именно должен появиться `OllamaProvider`;
- каким образом сейчас происходит dependency injection провайдера;
- где должен выполняться Context Budget Guard;
- какие существующие unit-тесты потребуется расширить;
- какие новые тесты необходимо добавить.

### Стоп-условие A — нарушение границ

Если анализ покажет, что TASK_011 требует:

- изменения Engine;
- расширения публичного API Engine;
- доступа к Storage или DexieStore;
- появления Selection / Retrieval / Search;
- собственного индекса / кэша / хранения состояния,

немедленно остановись и сообщи. Самостоятельно менять архитектуру
запрещено.

### Стоп-условие B — неоднозначность реализации

Если границы не нарушены, но в реализации остаётся неоднозначность
(например, размещение guard: метод в `AIService` или отдельный модуль) —
не разрешай её молча. Сформулируй развилку с вариантами и спроси, прежде
чем писать код. Фазы «анализ → подтверждение → реализация» не
сворачиваются.

## Фаза 2 — Реализация (строго в рамках TASK_011)

Реализовать только то, что описано в `tasks/TASK_011.md`:

- `OllamaProvider` за существующим интерфейсом `LLMProvider`;
- endpoint и модель — исключительно из конфигурации;
- Context Budget Guard;
- `ContextBudgetExceededError` с полями `actualChars`, `budgetChars`;
- dependency injection провайдера;
- `MockProvider` остаётся штатным провайдером для тестов;
- AI Layer остаётся stateless;
- публичный API Engine не изменяется.

### Запрещено добавлять

Дополнительные возможности, «улучшения», API «на будущее», второй
провайдер, tokenizer, подсчёт токенов, Selection, Retrieval, Search,
embeddings, streaming, citations, UI, CLI. Любая функциональность вне
TASK_011 считается нарушением задания.

не менять существующий публичный контракт AIAnswer и интерфейс LLMProvider, кроме реализации уже существующего интерфейса.


### Guard: размещение

Размести guard там, где проще и тестируемо. **Не создавай отдельную
абстракцию (класс/модуль) ради «чистоты», если guard не переиспользуется
и не требует изолированного тестирования сверх того, что уже покрывается
тестами AIService.** Лишняя абстракция под один вызов противоречит
принципу простоты. Если считаешь выделение оправданным — это развилка
по стоп-условию B, вынеси её.
